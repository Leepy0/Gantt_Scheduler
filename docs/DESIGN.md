# 설계

과제 진척 대시보드(TaskBoard)와 간트 스케줄러(GanttScheduler)를 하나로 합쳐 다시 설계한 내용. 두 프로젝트의 코드는 가져오지 않고 개념만 이어받았다.

## 1. 무엇을 합쳤나

| | 이전 TaskBoard | 이전 GanttScheduler | 통합 후 |
|---|---|---|---|
| 보는 범위 | 여러 과제를 넓게 | 과제 하나를 깊게 | 대시보드(넓게) → 과제 상세(깊게) |
| 구조 | 과제 → 단계(목표일/완료일) | 프로젝트 → 단계 → 작업(목표/실적 기간) | **과제 → 단계 → 작업** |
| 사용자 | 접속 IP ↔ 이름 | 자유 입력 담당자 | 사용자 한 종류(IP 는 여러 개 연결 가능, IP 없는 담당자도 허용) |
| 이력 | 변경 로그 | 댓글 + 계획 변경 로그 | 활동(댓글·변경) 한 스트림 |
| 위치 | 법인/제품군/라인/층 4개 테이블 | 없음 | 단일 트리 테이블(Location) |

핵심은 **단계는 약속 일정(마일스톤), 작업은 그 안의 세부 일정**이라는 구분이다. 소형 과제는 단계 날짜만으로 관리하고, 대형 과제만 단계 아래에 작업을 붙인다.

## 2. 확정한 규칙

1. **단계 목표일은 사람이 정한다.** 작업 일정에서 자동으로 덮어쓰지 않는다. 대신 작업들의 가장 늦은 예상 종료일을 "작업 기준 예상 종료"로 따로 보여 주고, 목표일을 넘으면 경고한다.
   - **예상 일정(오늘 기준 전진 계산, `Rules.ForwardPass`)**: 작업마다 오늘과 실적을 반영한 예상 시작·종료를 의존 관계를 따라 앞으로 전파한다(위상 정렬 한 번, O(작업+연결)). 완료 작업은 실적 그대로(완료된 단계의 작업은 단계 완료일에 끝남), 진행 중 작업은 종료 = max(목표 종료, 오늘)(같이 끝 선행이 늦어지면 그 뒤까지), 미착수 작업은 시작 = max(목표 시작, 오늘, 선행들의 예상 일정이 허용하는 가장 이른 날 — 규칙 11 의 `EarliestStart`)이고 근무일 기간은 그대로다. 목표가 그보다 늦으면 목표 그대로 둔다(앞으로 당기지 않는다). 진행 중인 선행이 늦어지면 아직 시작하지 않은 후행의 예상도 함께 늦어진다. 저장값은 바꾸지 않는다.
   - 단계의 "작업 기준 예상 종료" = 그 단계 작업들의 예상 종료 중 가장 늦은 날. 상세·Excel·PDF 와 대시보드·목록·주간 보고(조기 경보)가 모두 전진 계산을 쓴다 — 대시보드·목록은 작업까지 이미 읽으므로 작업 의존(`Links`)·근무일 달력·과제 간 연결만 더 읽는다(6장). 의존·달력을 넘기지 않는 옛 호출(시험의 순수 계산)만 작업마다 max(목표 종료, 오늘)을 보는 간단한 계산(`Rules.Forecast(s, today)`)으로 돌아간다.
   - **조기 경보(지연 위험·정체)**: '지연'은 목표일이 지난 단계만 센다. 그 전에 보이는 신호를 `Rules.RiskReasons` 한 곳에서 이유 목록으로 만든다 — 단계 예상 종료가 목표일을 넘음(가장 큰 초과 일수 = `RiskDays`, '예상 +n일'), 기한 지난 미완료 작업(완료 단계의 작업 제외), 기준선 대비 목표 종료가 `Rules.RiskSlipDays`(5)일 이상 밀림, 과제 간 단계 연결 위반(연결을 읽은 경로에서만). 진행 과제만 보고, **지연 위험** = 아직 지연이 아니고 이유가 있는 과제(`Rules.AtRisk` — 지연 과제는 '지연'으로 따로 센다). **정체** = 진행 과제의 마지막 변경(`Project.UpdatedAt`)이 `Rules.StaleDays`(14)일을 넘음 — 작업·단계·체크·댓글·첨부·연결 등 과제를 바꾸는 모든 경로가 `UpdatedAt` 을 갱신하므로(4장 '다른 사용자의 변경 알림') 따로 읽을 것이 없다. 방문·관심·읽음은 개인 설정이라 갱신하지 않는다. 색은 노랑(위험)이고 빨강은 지연에만 쓴다. 시작 지연(작업)은 상세의 칩으로 충분해 과제 이유에 넣지 않았다(같은 작업이 곧 '기한 지난 작업'이 된다).
   - **시작 지연**: 목표 시작일이 지났는데 아직 시작하지 않은 미착수 작업. 휴일에 시작하도록 적힌 작업은 다음 근무일에 시작하는 것으로 본다(밀기·재계획과 같은 기준 — 토요일 시작 작업은 월요일에 시작하면 늦지 않다). 목표 종료 전이면 지연(빨강)이 아니라 위험(노랑, '시작 지연' 칩)으로 보인다. 간트의 시작 전 점선 막대는 예상 일정에 그리고, 예상이 목표보다 늦으면 노랑 점선이다. 목록 보기는 '예상 MM-dd~MM-dd (+n근무일)'을 함께 적는다.
   - **재계획**(`ProjectService.ReplanAsync`): 예상과 목표가 다른 미착수 작업(밀기 대상, `Rules.ReplanMoves`)의 목표 일정을 예상대로 옮긴다. 상세 도구 모음의 '재계획'(대상이 있을 때만 보임) → 옮겨질 작업 표(서버 계산) → 사유 한 번 → 저장. 작업마다 `WorkPlanChanged` 1건·Version++, BatchId 하나. 화면이 본 목록(작업·버전·새 일정)을 함께 보내 그사이 계산이 달라졌으면 409 로 다시 보게 한다. 진행 중·완료 작업과 단계 목표일은 바꾸지 않는다(규칙 1 — 목표일은 사람이 정한다).
   - **저장 전 미리보기(What-if)**(`PreviewWorkPlanAsync`·`PreviewStageTargetAsync`·`ReplanPreviewAsync`, 상세 `GET ?handler=Preview`): 작업 일정 끌기·작업 시트(일정·단계·선행 연결·실적 — 실적 시작이 있으면 밀지도 선행을 검사하지도 않으므로 시트에서 고친 실적 시작·진행률을 저장과 같은 식으로 반영한다)·단계 목표일(시트·끌기, 연쇄 이동·작업 포함 선택 반영)·재계획 시트에서 입력이 바뀌면 0.3초 뒤 서버에 묻는다. 저장과 같은 검사(날짜 범위·선행)와 같은 계산(`Reschedule`·`CommitPlan`의 범위 검사·`ForwardPass`)을 과제를 새 객체에 옮겨 담은 복사본에 적용해 근무일 수, 함께 밀리는 작업(지금→바뀐 뒤·근무일 이동), 단계 예상 종료 전/후·목표 초과(지나간 목표일이면 빨강, 아니면 노랑), 저장이 막히는 이유(필드와 함께), 막지는 않지만 알아 둘 일(이미 시작해 밀지 않는 후행과 어긋남, 다른 과제 단계와 새로 어긋남), 휴일 안내를 돌려준다. 저장·활동·사용자 생성은 없다. 시트의 근무일 수·휴일 안내도 이 값을 쓴다(화면은 근무일을 세지 않는다).
   - **목표일 초안은 제안일 뿐이다.** 과제 등록 화면은 유형·착수일을 고르면 단계 템플릿의 기본 기간(`StageTemplate.DefaultWorkDays`, 근무일)으로 초안을 계산해 표로 보여 준다(`Rules.DraftTargets`). 앞 단계 목표일(첫 단계는 착수일)에서 근무일 기본 기간만큼 뒤이고, 기본 기간이 없는 단계는 비우며 그다음 단계는 앞에서 정해진 마지막 목표일부터 센다. 사람이 고친 줄(빈 값 포함)은 그대로 두고 그 뒤 단계만 거기서 다시 센다. 사람이 확인하고 등록해야 목표일이 되며, 서버가 저절로 채우지 않는다. 기본 기간은 과제에 복사하지 않는다(나중에 바꿔도 기존 과제에 영향 없음).
   - **같은 거리 하나**: 기본 기간·초안·단계 일정 표의 근무일 간격(`Rules.TargetGaps`, `StageView.GapWorkDays`)·관리 화면의 과거 평균 힌트가 모두 "앞 단계 목표일(첫 단계는 착수일)부터 이 단계 목표일까지의 근무일 거리(`WorkCalendar.Distance`)"를 쓴다. 초안을 그대로 두면 간격 = 기본 기간이고, 과거 평균을 기본 기간에 그대로 옮겨 쓸 수 있다.
   - **과거 평균 힌트**(`Reporting.StageLeadHints`): 같은 유형·같은 이름 단계가 완료된 과제(모든 단계 완료)에서 걸린 근무일(앞 단계 완료일부터)의 평균. 표본(과제)이 3건 이상일 때만 보인다(`LeadHintMinSamples`). 앞 단계와 같은 날 또는 먼저 완료한 기록(0 이하)은 몰아서 완료 처리한 것으로 보고 빼고, 기준점은 지금까지 가장 늦은 완료일로 둔다(순서를 거슬러 완료한 단계 뒤가 길게 잡히지 않게).
2. **진행률**: 단계 = 완료면 100, 작업이 있으면 작업 진행률 평균, 없으면 0. 과제 = 단계 진행률의 평균.
3. **상태는 저장하지 않고 계산한다** (단계·작업). 날짜와 상태가 어긋나는 일이 없다.
   - 단계: 완료일 있음 → 완료 / 목표일 지남 → 지연 / 순서상 첫 미완료 → 진행 중 / 나머지 → 예정
   - 작업: 실적 종료 있음 → 완료 / 실적 시작 있음 → 진행 중 / 없음 → 예정. 목표 종료가 지난 미완료는 지연, 목표보다 늦게 끝난 완료는 "초과 완료"
   - **완료된 단계의 작업은 단계와 함께 끝난 것으로 본다.** 실적 종료가 비어 있어도 지연·임계·내 할 일·다음 주 계획에서 빼고, 의존 관계로 밀지도 않는다(`Rules.IsOpen`·`IsMovable`). 화면은 이런 작업을 "완료(단계)"로 표시하고 실적 막대를 단계 완료일에서 끊으며, 간트에서 끌어 옮기지 않는다(`Rules.IsClosedByStage` → `ClosedOn`). 단계를 완료할 때 "남은 작업 n건을 완료일로 닫고 완료"를 고르면 작업마다 실적(시작이 없으면 목표 시작일, 종료는 완료일)과 진행률 100% 를 넣고 이력을 남긴다. 완료를 취소하면 그 단계의 미착수 작업을 그 사이 늦어진 선행에 맞춰 규칙 11 의 밀기로 다시 맞춘다(같은 BatchId 로 작업당 이력 1건).
4. **과제 상태**는 진행/보류/중단/완료. 완료는 모든 단계가 끝나면 자동으로 바뀌고, 완료 취소 시 다시 진행으로 돌아온다. 보류·중단은 사유 필수.
   - **종료일**(`Project.ClosedOn`, `Rules.ClosedOn`): 완료면 마지막 단계 완료일, 중단이면 중단 처리일(완료에서 중단으로 바꿔도 그날), 진행·보류는 없음. 상태가 바뀌거나 완료 과제의 단계 완료일을 고치는 경로가 모두 지나는 `SyncState` 에서 다시 계산해 저장한다 — 목록의 완료·중단 탭 연도 조건과 '올해 완료'가 단계 완료일을 매번 모으지 않고 DB 에서 범위로 거르기 위해서다. 종료일 열이 생기기 전의 과제는 서버 시작 단계(`StartupWork` → `DbInitializer`, `ClosedDates.FillAsync`)에서 한 번 채운다(값이 있으면 건너뛰어 멱등, 중단일은 마지막 '→ 중단' 상태 변경 활동의 한국 날짜).
5. **목표일을 바꿀 때는 사유 필수** (단계 목표일, 작업 목표 일정). 처음 정할 때는 사유 없이 기록만 남긴다.
   - 등록할 때 정한 목표일도 처음 정하는 것이라 "목표일 설정"(사유 없음)으로 남긴다. 단계 Id 는 저장 뒤에 정해지므로 이 기록은 단계명으로만 남긴다(단계 추가 기록과 같다).
   - **단계 일정 표**(상세 "단계 일정 편집", `ProjectService.SaveStageScheduleAsync`): 여러 단계의 목표일·완료일을 한 번에 저장한다. 화면은 바꾼 단계만 보내고, 서버는 단계마다 화면이 본 버전을 확인한다(바꾸지 않은 단계는 다른 사람이 동시에 고쳐도 충돌이 아니다). 이미 정한 목표일을 바꾸거나 지우는 단계가 하나라도 있으면 사유를 한 번 받아 그 단계들의 기록에 모두 남기고, 모든 기록(목표일·완료·작업 밀기)을 BatchId 하나로 묶는다. 완료는 단계 시트와 같은 내부 메서드(`EnsureCanComplete`·`SetCompleted`·`RealignReopenedAsync`)를 거친다 — 체크리스트가 남으면 거절, 완료 취소 시 그 단계 작업을 선행에 맞춰 밀기(여러 단계를 다시 열어도 한 번에 계산해 작업당 1건), 과제 자동 완료·재개. 표에서 완료하면 남은 작업은 "완료(단계)"로 본다(작업마다 실적을 넣으려면 단계 시트의 "남은 작업을 완료일로 닫고 완료"). 검사를 모두 통과한 뒤에만 값을 바꾸므로 한 줄이라도 거절되면 아무것도 바뀌지 않는다. 연쇄 이동은 표에서 모든 단계를 직접 고치므로 두지 않는다.
   - 표의 간격·추천 입고일은 고치는 동안 미리보기 요청(`SchedulePreviewAsync`, 저장하지 않음)으로 서버가 다시 계산한다(화면이 근무일을 세지 않는다). 동시 수정으로 거절되면 규칙 14 의 세 갈래 비교로 표를 최신 단계로 다시 그린다(삭제·추가된 단계 포함).
6. **연쇄 이동**: 단계 목표일을 바꿀 때 이후 미완료 단계를 같은 **근무일 수**만큼 함께 옮길 수 있다. 한 번의 사유로 묶어 기록한다(BatchId).
   - "이후 단계의 미착수 작업 n건도 같은 근무일 수만큼 이동"을 고르면(기본 꺼짐) 그 작업들도 근무일 기간을 지킨 채 옮긴다. 당겨서 앞 단계 선행과 어긋나는 작업은 규칙 11 의 밀기로 다시 맞춘다. 작업마다 처음 → 마지막 일정으로 이력 1건(같은 BatchId·사유).
7. **입고 추천일** = 검수 단계 일자(완료일 우선, 없으면 목표일) + 법인의 해상 운송 소요일. 입고 단계 편집 시 추천값으로 보여 준다. 단계 일정 표와 등록 초안도 같은 규칙(`Rules.InboundRecommendation`)으로 저장 전 날짜에서 계산해 "적용" 단추로 보여 준다. 초안은 추천일을 저절로 넣지 않는다(샘플 기준 정보의 입고는 법인마다 운송 기간이 달라 기본 기간을 비워 둔다).
8. **지연 판정의 '오늘'은 한국 시간** 기준. 법인별 시간대는 두지 않는다.
   - 화면은 페이지를 받을 때의 날짜를 계속 쓰지 않는다. 변경 응답·`/version`(1분마다·탭이 다시 보일 때)이 한국 날짜(`today`)를 싣고, 날짜가 바뀌었으면 상세 화면은 최신 과제를 다시 읽어 그린다(자정을 넘겨 열어 둔 화면이 어제 날짜로 저장하거나 지연 표시가 어긋나지 않게).
   - **실적 날짜의 기본값은 접속한 PC 의 날짜**다: '오늘 시작·오늘 완료' 단추, 미래 날짜 경고, 진행률만 올린 작업에 넣는 실적 시작. 해외 법인(한국보다 늦은 시간대)에서 저녁에 누르면 한국은 이미 다음 날이라 하루 뒤 날짜가 기록되기 때문이다. 화면이 PC 날짜(`clientToday`)를 보내고, 서버는 한국 날짜 ±1일(`Rules.ClientDayWindow`) 안이면 그 값을, 아니면(PC 시계가 틀림) 한국 날짜를 쓴다(`Rules.UserToday`). 단추가 넣는 날짜는 사용자가 고칠 수 있는 입력값이라 서버가 바꾸지 않으므로, 화면(`App.userToday`)이 같은 허용 범위를 서버에게서 받아(`data-day-window`) 지킨다.
9. 기준 정보는 지우지 않고 **사용 중지**한다(기존 과제에 계속 표시). 단계 템플릿과 공휴일만 바로 삭제한다. 단계 템플릿은 과제 생성 시점에 복사되므로 나중에 바꿔도 기존 과제는 영향이 없다.
    - 사용 중지/다시 사용 요청은 원하는 상태(`MasterRef.Active`)를 싣고 서버가 그 값으로 맞춘다(같으면 아무 일도 없다, 상태가 없는 요청은 거절). 뒤집기였을 때는 두 번 누르거나 오래된 화면에서 누르면 반대로 동작했다. 위험 단추는 응답까지 잠근다.
    - 과제가 쓰는 유형의 성격(기기·용기 내역)은 바꿀 수 없다(`subKind` 오류 — 새 유형을 만든다). 성격 값 없이 저장하면 지금 성격을 둔다. 과제 수정은 지금 성격 쪽 내역만 바꾸고 반대쪽(예전 성격의 내역)은 건드리지 않는다. 대분류로 고른 기기에 나중에 하위 타입이 생겨도 수정 화면이 "(대분류 전체)"로 남겨 그대로 저장된다.
    - **공휴일**: 서버는 시작할 때마다 내장 목록(정부가 확정 발표한 해 — 지금 2026~2027)의 해 중 공휴일이 하나도 없는 해만 채운다(관리자가 일부를 지운 해는 다시 채우지 않는다). 확정 전인 해는 넣지 않고 10월부터 관리자 알림(내년 공휴일 없음)과 관리 화면 연도 칩의 경고로 알린다. 관리 화면은 연도별로 보이고 여러 줄 붙여넣기('날짜 TAB/공백 이름', 한 줄이라도 틀리면 아무것도 넣지 않음, 이미 있는 날짜는 건너뜀)를 받는다. 공휴일을 저장·삭제·붙여넣으면 응답에 영향을 알린다(`Rules.HolidayImpact`): 바뀐 날이 미완료 단계 목표일이거나 열린 작업 기간 안인 진행 과제 수와, 선행 관계를 새로 어기게 된 밀기 대상 작업 수. 일정을 자동으로 밀지는 않는다.
    - **유형 템플릿 작업**: 관리 > 유형·단계에서 단계 템플릿 아래에 작업 템플릿(작업명·시작·기간·선행)을 둔다. 과제를 등록할 때('템플릿 작업 n개 함께 만들기', 기본 켬) 단계마다 작업으로 복사한다 — 단계·체크리스트와 같이 등록 시점 복사라 나중에 템플릿을 바꿔도 기존 과제는 그대로다.
      - 날짜: 단계 시작 기준일(`Rules.StageStarts`)에서 시작 근무일(`OffsetWorkDays`)만큼 뒤에 시작해 기간(`DurationWorkDays`, 근무일)을 차지한다(`Rules.PlaceTemplateWork`). 첫 단계의 기준일은 착수일(휴일이면 다음 근무일), 이후 단계는 앞에서 정해진 마지막 목표일의 다음 근무일이다 — 목표일 초안(`DraftTargets`)과 같은 '앞 단계 목표일부터 이 단계 목표일까지'를 그 단계의 기간으로 본다. 앞 단계 목표일은 등록에서 정한 값이고, 비워 둔 단계는 기본 기간 초안을 쓴다(목표일을 정하지 않아도 작업이 착수일에 몰리지 않게). 앞에 정해진 목표일이 하나도 없으면 착수일이다.
      - 선행은 같은 단계 템플릿 안의 다른 작업 템플릿만 고를 수 있고(순환 거절), 과제에서는 '끝나면 시작'·간격 0 연결이 된다. 템플릿 값이 선행과 어긋나면 등록할 때 밀기(규칙 11)로 선행 뒤에 놓는다(복제와 같은 처리). 담당은 과제 담당, 활동은 작업마다 '작업 추가 (유형 템플릿)'를 목표일 설정과 같은 묶음으로 남긴다.
    - 입력 길이 상한은 `Domain/Limits.cs` 한 곳이다 — DB 열 길이(`HasMaxLength`)·서비스 검사·관리 화면 maxlength 가 같은 값을 쓴다(SQL Server 만 길이를 검사해 생기던 500 을 없앤다).

10. **근무일**: 주말과 관리 화면의 공휴일을 뺀 날. 기간 표시(근무일 n일), 연쇄 이동, 의존 관계에 따른 일정 밀기, 여유, 복제에 쓴다. 지연 일수(D+n)는 달력 날짜 기준 그대로다.
    - 계산은 "그날까지의 누적 근무일 수"를 주 단위 산술과 정렬된 공휴일 목록의 이분 탐색으로 구해 그 차이로 한다(`WorkCalendar`). 기간이 길어도 하루씩 돌지 않고, 날짜 끝에서 넘치지 않는다.
11. **의존 관계**는 선행 작업마다 유형과 간격(근무일, 0~250)을 둔다. 판정은 모두 `Rules.EarliestStart(link, 선행 시작, 선행 종료, 후행 근무일 기간)` 하나를 거친다 — 밀기·저장 검사·여유·위반 표시·전진 계산(규칙 1)이 같은 답을 쓴다.
    - **끝나면 시작(FS, 기본)**: 후행은 선행 종료 다음 근무일 + 간격 이후에 시작한다.
    - **같이 시작(SS)**: 후행은 선행 시작일(휴일이면 다음 근무일) + 간격 근무일 이후에 시작한다. 같은 날 시작해도 된다.
    - **같이 끝(FF)**: 후행은 선행 종료일 + 간격 근무일 이후에 끝난다. 같은 날 끝나도 된다. 선행 종료일이 휴일이면 FS 처럼 직전 근무일에 끝난 것으로 본다(토요일 종료로 적힌 선행 + 간격 0 → 후행은 금요일에 끝나도 된다. 다음 근무일로 올리면 간격 0 이 간격 1 처럼 된다). 판정은 후행의 근무일 기간만큼 거꾸로 센 시작일로 하므로 밀기도 기간을 지킨 채 끝을 맞춘다.
    - 휴일에 시작하는 것으로 적힌 작업은 다음 근무일에 시작하는 것으로 보고 판정한다(`Rules.StartsBefore` — 밀기의 `Place` 와 같은 기준).
    - 입력: 작업 시트에서 선행마다 유형·간격을 고른다(`WorkInput.Links[{predecessorId, lagDays, type}]`). 예전 형식 `Predecessors`(id 목록)도 받는데, 새 연결은 FS·간격 0 이고 이미 있던 연결은 유형·간격을 그대로 둔다(유형을 모르는 화면이 저장해도 지우지 않게). 연결 추가·삭제·유형·간격 변경은 연결마다 `LinkChanged` 이력을 남긴다. 간트의 연결선은 유형에 따라 잇는 쪽이 다르다(FS 끝→시작, SS 시작→시작, FF 끝→끝). 복제는 유형·간격을 그대로 복사한다.
    - 순환 연결은 유형과 관계없이 그래프로 보고 거절한다. 사람이 입력한 일정이 선행보다 이르면 거절하는데, **밀기 대상(미착수·단계 미완료) 작업이 새로 생기거나, 그 작업의 목표 일정·선행 연결(집합·유형·간격)을 바꾸거나, 실적 시작을 지우거나 열린 단계로 옮겨 밀기 대상이 될 때만** 검사한다. 제목·담당·메모·진행률만 고칠 때는 이미 남아 있던 위반(공휴일 추가 등으로 생긴)이 있어도 저장되고, 위반은 화면에 표시된다. 밀기·위반 표시·이 검사는 모두 같은 판정(`Rules.IsMovable`)을 쓴다 — 이미 시작했거나 완료된 단계의 작업은 밀지도, 위반으로 표시하지도, 날짜를 검사하지도 않는다.
    - 선행 일정이 늦어지면 **아직 시작하지 않은** 후행은 근무일 기간을 유지한 채 자동으로 밀린다(`Rules.Reschedule`). 바뀐 작업에서 닿는 후행만 위상 정렬 순서로 보고, 선행이 여럿이면 모든 선행이 정해진 뒤 가장 늦은 요구에 맞춰 **한 번만** 옮긴다. 이력은 작업당 1건(같은 BatchId). 이미 시작한 후행과 완료된 단계의 작업은 건드리지 않고, 앞으로 당기지는 않는다.
    - **여유** = 일정을 미뤄도 단계 목표일과 후행 작업에 영향이 없는 **근무일 수**. 목표일이 주말이고 작업이 직전 금요일에 끝나면 여유 0 이다. 미완료이고 여유가 0 이하인 작업이 **임계 작업**이다. 후행과의 틈도 `EarliestStart` 로 재므로 유형을 따른다(같이 시작인 후행이 꽉 차 있으면 선행도 임계).
    - **과제 간 단계 의존**(`StageLink`): 서로 다른 과제의 단계를 "선행 단계 완료일(없으면 목표일) 다음 근무일 + 간격 이후에 후행 단계 목표일"로 잇는다(`Rules.StageLinkEarliest`·`StageLinkViolated`). **자동으로 밀지 않고 위반만 계산한다** — 다른 과제 담당자의 일정을 몰래 바꾸지 않기 위해서다. 후행 단계가 완료됐거나 어느 쪽이든 날짜가 없으면 판정하지 않는다. 위반은 두 과제 상세의 단계에 경고 칩(누르면 상대 과제로 이동)과 간트 이름 칸 아이콘으로 보이고, `ProjectView.LinkViolations`(위반 연결 수)로 노출한다. 상세는 그 과제 단계의 연결을, 대시보드·목록은 연결 표 전체를 한 번 읽어(`AllCrossLinksAsync`, 휴지통 과제와의 연결은 뺀다) 세고 조기 경보의 이유가 된다. 연결을 넘기지 않는 계산에서는 0(위반 없음)과 구별되게 null(모름)이다. 단계 시트의 "다른 과제 단계에 연결"에서 방향(선행·후행) → 과제 검색 → 단계 → 간격을 골라 잇는다. 같은 과제끼리·같은 쌍·과제 간 연결을 따라 되돌아오는 순환은 거절한다. 연결·해제는 두 과제 모두에 `LinkChanged` 이력을 남기고 변경 시각을 갱신한다(열린 상대 과제 화면에 변경 띠). 단계·과제를 지우면 서비스가 그 연결을 먼저 지우고 상대 과제에 이유를 남긴다(두 FK 모두 Restrict — 같은 단계 테이블로 가는 cascade 경로가 둘이면 SQL Server 가 거절한다). 복제는 과제 간 연결을 복사하지 않는다. 단계 목표일 미리보기는 이 변경으로 새로 어긋나는 연결을 (막지 않고) 알린다.
12. **기준선**은 "기준선 확정"을 누른 시점의 단계 목표일·작업 목표 일정을 따로 저장한 것이다. 이후 일정이 바뀌면 기준선 대비 +n일로 보여 준다. 다시 확정하면 '최신 기준선'이 바뀌어 밀린 일수가 0 으로 돌아간다 — 그래서 **다시 확정은 과제 담당자·관리자만**(`Rules.CanRebaseline`), **사유 필수**, 이력의 OldValue/NewValue 에 직전·새 목표 종료일을 남기고 과제 버전을 확인한다. 처음 확정은 누구나 한다.
    - **차수 이력**: 확정할 때마다 새 차수(`Baseline` No 1, 2, …: 시각·사람·사유)와 그때의 단계 목표일·작업 목표 일정(`BaselineItem`)을 더한다. 덮어쓰지 않으므로 이전 기준선을 언제든 다시 볼 수 있다. 기존 열(`Stage.BaselineDate`, `WorkItem.BaselineStart/End`, `Project.BaselineAt`)은 **최신 차수의 사본**으로 그대로 둔다 — 목록·대시보드·Excel·PDF·리드타임은 예전처럼 최신 기준선을 쓴다. 활동 문구에 차수를 적는다('기준선 다시 확정 (2차, …)').
    - **비교 기준**: 상세 > 정보의 '기준선 이력'에서 차수(최신·직전·1차 …)를 고르면 서버가 그 차수의 값을 읽은 그래프의 기준선 열에 넣고(`Rules.UseBaseline`) 같은 규칙(`Rules.SlipDays(지금, 기준)`)으로 단계·작업·과제의 +n일과 간트 기준선 막대를 다시 계산한다. 화면은 고른 차수를 모든 요청 주소에 `?compare=n` 으로 붙여 저장 뒤 응답도 같은 기준으로 받는다. 그 차수 뒤에 생긴 단계·작업은 기준값이 없다. 최신이거나 없는 차수는 최신 그대로(`ProjectView.CompareNo` = null).
    - 단계·작업 Id 는 느슨한 참조라 지워도 차수 기록은 남는다. 복제는 기준선(차수 포함)을 가져가지 않는다(규칙 15).
    - **기존 데이터 이전**: 차수 이력이 생기기 전에 확정한 과제(`BaselineAt` 은 있는데 차수가 없음)는 서버 시작 단계(`StartupWork` → `DbInitializer`)에서 지금의 기준선 열로 1차를 한 번 만든다(`BaselineHistory.EnsureFirstRoundsAsync`, 차수가 있으면 건너뛰어 멱등). 확정한 사람·사유는 마지막 '기준선 확정' 활동에서, 없으면 과제 담당자로 둔다.
13. **체크리스트**: 단계에 체크 항목을 둘 수 있고, 남은 항목이 있으면 단계를 완료할 수 없다. 유형의 단계 템플릿에 기본 항목을 넣어 두면 과제 생성 시 복사된다.
14. **동시 수정**: 과제·단계·작업에 버전 번호를 둔다. 화면이 읽은 버전과 저장 시점의 버전이 다르면 저장을 거절하고(HTTP 409) 화면을 최신 내용으로 바꾼다. 뒤에 저장한 사람이 앞사람 내용을 모르고 덮어쓰는 일을 막는다.
    - 삭제(단계·작업·체크 항목)와 체크 토글·문구 수정도 화면이 본 버전을 받는다. 체크리스트는 단계의 완료 조건이라 **단계 버전**으로 가리고 바꾸면 단계 버전을 올린다. 단계 시트는 자기 체크 변경 뒤 시트가 저장하는 칸(이름·목표일·완료일)이 그대로면 새 버전을 받아들여 스스로 충돌하지 않는다. 체크 문구 수정은 '옛 → 새' 이력을 남기고 완료한 단계에서는 거절한다.
    - 단계 순서 변경은 두 단계의 버전과 화면이 본 이웃 단계를 확인하고 둘 다 버전을 올리며 "단계 순서: A ↔ B" 이력을 남긴다(순서가 현재 단계 판정·연쇄 이동 범위를 정한다).
    - 일정 변경 **횟수는 결정 단위**로 센다(`Rules.DecisionCount` — 같은 BatchId 의 연쇄 이동·선행 연동 행은 1회). 상세의 목표일 변경 수·주간 보고·Excel·PDF 가 같다.
    - 거절된 편집 창(상세 시트·끌기 사유 창·과제 수정 화면)은 닫지 않고 최신 버전으로 바꿔 **같은 창에서 다시 저장**할 수 있게 한다. 칸마다 세 갈래(연 때의 값·최신 값·지금 입력)로 비교해, 내가 손대지 않은 칸은 최신 값으로 바꿔 넣고("다른 사용자가 바꾼 값: … — 그 값으로 바꿨습니다"), 둘 다 바꾼 칸은 내 입력을 두고 상대 값을 옆에 보인다. 손대지 않은 칸을 옛 값 그대로 다시 저장하면 앞사람의 변경을 되돌리기 때문이다. 과제 수정 화면은 연 때의 값을 숨은 입력(`Form.Base`)으로 들고 다닌다(표시용, 저장에는 쓰지 않는다). 읽기와 저장 사이에 끼어든 변경(`DbUpdateConcurrencyException`)도 같은 방법으로 처리한다.
15. **과제 복제**: 단계·체크 항목·기기/용기 내역을 복사하고, 날짜는 원본 착수일로부터의 **근무일 거리** 그대로 새 착수일에 맞춰 옮긴다(작업은 근무일 기간 유지). 달력 일수로 옮기면 요일이 바뀌어 주말에 놓이거나 기간이 줄고 의존 위반이 생기기 때문이다. 남은 위반은 규칙 11 의 밀기로 정리한다. 작업과 의존 관계는 선택. 실적·진행률·완료·활동·첨부·기준선은 복사하지 않는다.
16. **날짜 범위**: 단계 목표·완료일, 작업 목표·실적 일자는 2000-01-01 ~ 2099-12-31 이면서 과제 착수일 1년 전 ~ 10년 뒤 안이어야 한다. 착수일(등록·수정·복제)은 오늘 기준 앞뒤 10년. 연도 오타 하나가 근무일 계산이나 간트 그리기를 멈추게 하지 않도록 서버에서 거절한다(`Rules.ValidateDate`). 바뀐 날짜만 검사하므로 이전에 들어간 값이 있어도 다른 수정은 막지 않고, 착수일을 옮겨 기존 일정이 범위 밖이 되면 거절한다.

17. **일별 진척 스냅샷**: 상태·지연은 저장하지 않으므로(규칙 3) 과거 시점의 진행·지연 과제 수는 하루 한 번 남기는 스냅샷(`ProjectSnapshot`)에만 있다. `SnapshotWorker` 가 시작 직후 오늘 것이 없으면 바로, 그 뒤로는 한국 시각 `Snapshot:Hour`(기본 18시) 이후 한 번 더 남긴다(같은 날은 덮어쓰고, 그 사이 대상에서 빠진 과제의 오늘 행은 지운다). 대상은 휴지통이 아닌 진행·보류 과제와 그날 끝난 완료 과제(`Rules.InSnapshot`)이고, 값은 대시보드와 같은 계산(`Dashboard.ViewOf` — 진행률·지연·예상 지연·지연 위험·목표 종료·기준선 대비·현재 단계)과 그날의 유형·법인·담당·담당자 소속이다. 서버가 꺼져 있던 날은 지어내지 않는다(행이 없고 그래프도 그 사이를 잇지 않는다). 과제·활동은 읽기만 하고 활동을 남기지 않는다. 스냅샷은 추세·'전주 대비'·신규 지연/지연 해소에만 쓰고 지금 상태 표시에는 쓰지 않는다. 영구 삭제하면 과제 cascade 로 함께 지운다.
18. **지연 사유 분류**: 일정 변경 사유(단계 목표일·작업 목표 일정·끌기·재계획·단계 일정 표)에 선택 사항으로 분류(`DelayReason` — 관리 > 지연 사유, 다른 기준 정보처럼 지우지 않고 사용 중지)를 고른다. 사유를 남긴 `TargetChanged`·`WorkPlanChanged` 활동에 `Activity.ReasonCode`(FK 없는 느슨한 참조 — 분류를 사용 중지해도 옛 기록이 남는다)로 붙는다. 새로 고를 때는 사용 중인 분류만 받는다(`reasonCode` 오류). 진행률이 바뀐 작업 변경 활동은 문구는 그대로 두고 `OldValue`/`NewValue` 에 이전·새 진행률(숫자)을 더 남긴다 — 과제별 '진척 +n%p'(`Rules.ProgressGain`: 작업의 변화량 ÷ 그 단계 작업 수 ÷ 단계 수, 지금 구조로 환산, 값이 없는 옛 기록은 세지 않음)를 계산하기 위해서다. 단계 완료·완료 취소도 단계 진행률을 바꾸므로 함께 센다: `StageCompleted` 는 비어 있던 `OldValue` 에 완료 직전 단계 진행률을, `StageReopened` 는 비어 있던 `NewValue` 에 취소 뒤 단계 진행률(작업 평균)을 남기고(날짜를 담은 다른 쪽은 그대로), 변화량 ÷ 단계 수를 더한다(`Reporting.StageProgressChanges`) — 작업이 없거나 작업을 닫지 않고 완료한 단계도 오른다. 두 번 세지 않도록 단계 완료로 닫은 작업과 완료된 단계 안 작업의 진행률 변경에는 값을 남기지 않는다.
19. **일정 변경 분석**: 목표일·작업 일정 변경을 (BatchId ?? Id) 결정 단위로 묶는다(`Reporting.ScheduleChanges` — 주간 보고·`Rules.DecisionCount` 와 같은 묶음). 결정이 밀어낸 일수 = 묶음 안 (새 − 이전) 달력 일수의 최댓값(작업 값 'a~b' 는 종료일, '미정' — 처음 정함·지움 — 은 셀 수 없어 뺀다). 월별 밀림·누적 밀림은 양수만 더한다(당긴 결정이 밀림을 지우지 않게). 원인 파레토는 분류된 결정만으로 비율·누적 비율을 내고 분류 없는 결정 수는 따로 보인다.
20. **단계 병목**: 진행 과제의 지금 단계에 머문 근무일 = 앞 단계 완료일 중 가장 늦은 날(첫 단계는 착수일)부터 오늘까지(`Rules.StageEntered`·`StageDwell` — 리드타임 표본과 같은 기준점·단위). 같은 유형·같은 이름 단계의 평균 소요일(근무일, 표본이 있을 때)을 넘으면 '평균 초과'다.
21. **부하**(`Rules.Load`): 사람 × 주(월~일)의 배정 근무일 ÷ 가용 근무일. 진행 과제의 열린 작업(`IsOpen`)마다 담당 1.0·부담당 0.5를 그 작업이 걸린 기간의 근무일만큼 더한다. 기간은 오늘 기준 예상 일정(`ForwardPass`)이고 오늘 이전 몫은 빼서, 늦어진 작업이 지난 주에 묻히지 않고 남은 기간으로 잡힌다. 가용 근무일은 `WorkCalendar` 로 센다(공휴일이 낀 주는 줄어든다). 100% 를 넘으면 과부하(노랑).
22. **조직 범위**: 조직 조건은 과제 담당자의 소속으로 보고 그룹을 고르면 그 아래 파트까지 포함한다(`Rules.InOrg`). 대시보드·목록(`ProjectFilter.OrgUnitId`, `DashboardQuery.OrgUnitId`)·기간 보고·분석 탭이 같은 판정을 쓴다. 부하는 사람의 소속으로 묶고, 접속한 적이 없는(IP 없는) 이름만 등록된 담당자도 포함한다.

규칙 구현은 `Domain/Rules.cs`(계산), `Domain/WorkCalendar.cs`(근무일), `Services/ProjectService.cs`(변경 검증)에 있다.

- `StageLink(PredecessorStage, SuccessorStage, LagDays, CreatedAt)` 는 서로 다른 과제의 단계를 잇는다(규칙 11). 두 FK 모두 Restrict 이고 (선행, 후행) 쌍은 하나만 둔다(고유 색인). 단계·과제를 지울 때 서비스가 먼저 지운다.
- 휴지통(5장): `Project.DeletedAt` 이 있으면 휴지통에 있는 과제다. 지운 사람(`DeletedById`)은 Restrict, 정리 대상 고르기를 위해 `DeletedAt` 색인을 둔다. `Baseline` 은 과제 cascade·사용자 Restrict, `BaselineItem` 은 차수 cascade 한 길이다(단계·작업으로 가는 FK 없음).
- `TemplateWork` 는 단계 템플릿 아래의 작업 템플릿이다(규칙 9). 단계 템플릿 cascade, 선행(`PredecessorTemplateWorkId`)은 같은 표를 가리키므로 NoAction 이다(SQL Server 다중 cascade 경로를 피한다). 템플릿 작업이나 단계 템플릿을 지울 때 서비스가 먼저 선행을 끊는다.
- 과제의 `CorporationId` 는 `LocationId` 의 최상위(법인)를 미리 풀어 둔 값이다. 법인별 집계를 간단히 하기 위해서다.
- `Activity.StageId / WorkItemId` 는 FK 가 아닌 느슨한 참조다. 단계·작업을 지워도 이력은 남는다.
- 협력사는 과제에 문자열로 저장한다. 관리 화면의 협력사 목록은 자동완성 후보로만 쓴다(목록에 없는 이름도 입력 가능).
- `Version` 은 EF 의 동시성 토큰이다. 저장할 때 서비스가 1씩 올리고, UPDATE 의 WHERE 에도 들어가 읽기~저장 사이에 끼어든 변경을 DB 수준에서도 잡는다.
- 첨부 파일 본문은 DB 가 아니라 디스크(`Storage:Path/과제번호/임의이름`)에 둔다. 원래 파일 이름은 DB 에만 있어 경로 조작 위험이 없다. 허용 확장자만 받는다. 상한은 `Storage:MaxMB`(기본 30, 1~500) 하나 — 요청 크기 한도는 특성에 끝값(500MB)을 두고 요청마다 그 값으로 좁힌다. 기록을 지운 뒤 파일·폴더를 지우지 못하면(내려받는 중 등) 경고 로그만 남기고 성공으로 답한다(고아 파일 정리가 치운다). 내려받기는 `FileShare.Read|Delete` 로 열고 ETag(저장 이름 — 내용 불변)·범위 요청·`Cache-Control: private`.
- 사용자의 소속은 조직(OrgUnit) 참조다. 파트에 속하면 "그룹 · 파트"로, 그룹 직속이면 그룹 이름만 표시한다.
- 시각은 UTC 로 저장하고 화면에서 현지 시각으로 바꾼다. 날짜는 `DateOnly`.
- 협업 표(4.1): 사용자 FK 는 모두 Restrict(사용자는 지우지 않고 사용 중지한다). `Notification` 은 활동을 가리키는 FK(cascade)만 두고 `ProjectId` 는 느슨한 참조다 — 과제 → 활동 → 알림 한 길로만 지워지게 해 SQL Server 의 다중 cascade 경로를 피한다. `Notification.Key` 는 유일 색인이고, 읽지 않은 수·최근 순 목록을 위해 `(UserId, ReadAt)`·`(UserId, CreatedAt)` 색인을 둔다. 댓글을 고치면 첫 원문을 `Activity.OldValue`(1000자)에 남긴다.

화면 구성 원칙:

- 상세 화면은 서버가 준 JSON 하나로 그리고, 변경할 때마다 서버가 최신 과제 전체를 돌려줘 다시 그린다. 클라이언트에 계산 규칙을 두지 않는다. 활동만은 최근 50건(`ProjectService.ActivityPageSize`)과 전체 건수(`activityTotal`)를 싣고, 나머지는 `?handler=Activities&id=&beforeId=`(최근 순, `At`·`Id` 커서)로 나눠 받는다. 화면은 받아 둔 활동과 변경 응답의 최근 활동을 합쳐 그리므로 '더 보기'로 펼친 목록이 저장 뒤에도 남는다. 작업 시트의 진행 내용은 `&workId=` 로 그 작업의 활동만 받는다. 활동 필터·새 소식 같은 기능도 이 조회에 조건을 더해 만든다.
- 간트는 `wwwroot/js/gantt.js` 하나를 대시보드와 상세가 같이 쓴다. 외부 라이브러리·CDN 없음(사내망).
- 간트 끌기는 마우스·펜에서만 동작한다. 터치에서는 화면 스크롤과 겹치므로 막대를 눌러 시트에서 날짜를 고친다. 끌어서 목표 일정을 바꿔도 사유 입력은 똑같이 거친다.
- 모바일: 하단 탭, 과제 상세는 목록 보기가 기본(간트로 전환 가능), 편집 창은 아래에서 올라오는 시트. 입력 요소 48px.
- 색: 평소에는 중립색 + 강조색(#1428A0)만 쓰고, 빨강은 지연, 노랑은 임박·초과 완료에만 쓴다. 상태는 색과 함께 아이콘·글자로 표시한다.
- **기간 보고**(`InsightService.ReportAsync(from, to, ProjectFilter)` — 주간 보고의 일반화): 기간은 주(월~일)·월·직접 지정(상한 `Reporting.MaxReportDays` 92일, 넘으면 끝에서 상한만큼으로 줄이고 안내). '다음 기간 계획'은 보고 기간과 같은 길이다(한 달 전체 — 1일~말일 — 면 다음 달 1일~말일). 범위는 전체/내 과제와 유형·법인·조직(규칙 22), '변동 있는 과제만'(이번 기간 기록이 없는 과제는 카드·접힌 표 모두에서 뺀다 — 지연은 요약 표에 남는다). 첫머리에 **지연·위험 요약**(과제·지연 단계·D+n 또는 예상 +n일·최근 사유·담당), **기간 미달**(목표일·목표 종료일이 기간 안이고 기준일까지 지났는데 끝나지 않은 단계·작업 — `Rules.MissedIn`, 이번 기간이면 오늘 목표는 아직 아니다), **지연 변화**(직전 기간 끝 일주일 안 가장 늦은 스냅샷과 견준 새로 지연·지연 해소)를 둔다. - **대시보드 막대**: 유형·법인 막대는 진행·보류 과제와 올해 끝난 완료 과제만 센다(`Dashboard.InBars`) — 역대 완료·중단까지 세면 진행·지연 비교가 묻힌다. 막대를 누르면 같은 범위의 목록(`current=true` — '진행·보류와 올해 완료' 조건 안내)으로 간다.
- **주간 보고**(`Reporting.Weekly`): 일정 변경은 (BatchId ?? Id) 결정 단위로 세고 함께 옮겨진 대상은 접어 '일정 변경 n건(대상 m건)'. 상태 변경·기준선 확정과 자동 완료(모든 단계 완료)는 일정 변경에서 빼 따로 센다. 기한이 지난 단계·작업은 '밀린 항목'(D+n, 담당). 지연 과제는 변동이 없어도 카드, 나머지 무변동 과제는 끝의 표 하나. 지연·밀린 항목은 **보고 기준일 = min(그 주 마지막 날, 오늘)** 기준이라 지난 주를 다시 열어도 그 주 모습이다(그 뒤의 완료·실적은 아직 없던 것으로 — `Rules.DelayDaysAsOf`). 그 주가 끝난 뒤 등록한 과제는 넣지 않는다. 진행률·현재 단계와 목표일은 지금 값이다(스냅샷이 없다 — 화면이 밝힌다). 실적은 날짜로 판정한다(단계 완료일·작업 실적 종료일이 그 주 안).
- **리드타임**(`Reporting.LeadSamples` — 기본 기간 힌트와 같은 표본): 앞 단계 완료일(지금까지 가장 늦은 완료일, 첫 단계는 착수일)부터. 근무일 0 이하 표본(몰아서 완료)은 수를 보이고 평균에서 뺄 수 있다. '처음 목표'는 첫 목표일 변경의 이전 값이다 — 지금 목표일은 미룰 때마다 덮여 여러 번 미룬 단계가 지킨 것처럼 보이기 때문이다. **종료 연도**(`?year=`)를 고르면 그 해에 끝난(종료일) 완료 과제만 센다 — 해마다 공정·인원이 달라 평균을 해별로 견주기 위해서다. 이때 진행 과제가 없으므로 '진행 중 · 평균 초과' 열은 비어 있다.
- **대시보드·목록 정리**: 대시보드 조건(유형·법인·내 과제·간트 범위 `scope`·정렬 `sort`)은 URL 쿼리다(`DashboardQuery` — 링크로 보내도 같은 화면). 간트 기본 범위 '주요'는 지연 + 지연 위험 + `Dashboard.FocusDays`(28)일 안 목표가 있는 과제다 — 진행 과제가 수백 건이면 전체 간트는 훑어볼 수 없다. '전체 보기'로 모든 진행 과제를 본다. 화면 안의 링크는 늘 `scope` 를 실어 보내고, 쿼리 없는 `/`(다른 화면에서 온 것)는 마지막 조건(`App.pref` — 저장소를 못 쓰면 기본 조건)으로 다시 연다. '조건 해제'(`reset=1`)는 기억도 지운다. 목록 정렬은 `ProjectFilter.Sort/Desc`(`Dashboard.SortKeys`·`Dashboard.Sort` — 목록·Excel·대시보드 간트 공용, 값 없는 행은 방향과 관계없이 뒤, 같은 값이면 과제명 → Id)이고, 정렬 없이 열면 기억한 정렬로 연다('기본 순서'를 고르면 지운다). 숫자 링크는 유형·법인 조건을 함께 싣는다.
- **조기 경보 표시**: 대시보드 '지연 위험' 카드는 예상 지연 큰 순으로 `Dashboard.RiskShown`(8)건과 이유, 최근 사유 한 줄(최근 `RecentNoteDays`(60)일 안의 사유가 붙은 변경 또는 댓글 중 가장 최근 것 — 지연 카드에도 붙는다)을 보인다. KPI '위험 n · 정체 n'의 두 숫자는 각각 목록의 위험·정체 탭으로 간다(같은 판정이라 건수가 같다). 목록 행은 상태 칩 옆에 노랑 '예상 +n일'(또는 '위험')과 '정체' 칩, 간트 이름 칸은 '+n'(노랑)·'정체'를 보인다. 주간 보고는 **이번 주 보고에서만** 과제 머리에 '예상 지연 +n일' 칩을 싣고(지금 계산이라 지난 주 보고에는 없다), 그런 과제는 변동이 없어도 카드로 보인다. Excel(상태 칸 아래)·PDF(과제 메타 줄)에도 같은 글자를 적는다 — 카드 기준이 같으므로 왜 접히지 않았는지 보고서만으로 알 수 있게.
- **빠른 갱신**(내 할 일 행·작업 시트 맨 위, `wwwroot/js/quick.js` 한 조각): 진행률 칩(0/25/50/75/100 + 직접 — 시트는 슬라이더), '오늘 시작'·'오늘 완료'(접속자 PC 날짜, `App.userToday`), 진행 내용 한 줄. 저장 규칙은 작업 저장과 같은 `Rules.WorkActuals`·`ValidateActuals`(실적 종료가 있으면 100%, 진행률만 올리면 그날 시작, 5 단위)다. 내 할 일은 칩·단추를 누르는 즉시 `?handler=Progress`(`ProjectService.UpdateWorkProgressAsync` — 작업 버전 확인, `WorkEdited` 활동, 진행 내용은 작업 댓글)로 저장하고, 서버가 그 행을 다시 나눠(`Reporting.MyGroup`) 돌려주면 그 행만 바꾸거나 다른 묶음으로 옮긴다(완료하면 뺀다). 실적을 지우는 단추는 없다(지우면 밀기 대상이 되어 선행 검사가 필요하므로 작업 시트에서 한다). 409 는 최신 행으로 다시 그리고 입력한 진행 내용은 남긴다. 그 사이 다른 사람이 완료했거나 담당을 바꿔 내 할 일에서 빠졌으면 409 의 행이 null 이고 화면은 그 행을 빼며 알린다(옛 값으로 남기면 누를 때마다 409 가 난다). 작업 시트는 칩·단추가 아래 입력칸을 채울 뿐이고 저장 단추로 함께 저장하며, 진행 내용 한 줄은 저장 뒤 작업 댓글로 남긴다. 작업명·단계·담당·일정·선행·메모는 `<details>` 로 접고(새 작업은 펼침), 펼침 여부를 기억한다. 접힌 칸에 걸린 저장 오류는 펼쳐 보인다. 모바일은 칩·입력칸 48px.
- **대시보드 숫자 → 목록**: '올해 완료'·'7일 내 목표'·유형·법인 막대·다가오는 일정 '과제 n건 모두 보기'는 같은 판정의 목록 조건(`doneYear` — 종료일 `Project.ClosedOn` 의 연도, `due` — `Rules.HasStageDueWithin`, 유형·법인 Id)으로 잇는다. 막대는 이름이 아니라 Id 로 묶는다. 목록이 과제를 보이므로 숫자도 과제 수로 센다(단계가 둘 걸린 과제도 1).
- **표시 규칙은 서버 한 곳**: 임박은 목표일까지 `Rules.SoonDays`(7)일 이하, 단계 초과 완료(`StageView.DoneLate`), 작업의 기준선 대비·지연 일수(`WorkView.SlipDays`·`LateDays`)를 서버가 채운다. 상태 칩(색·아이콘·글자)은 `Views.ProjectChip·StageChip·WorkChip·DueChip` 이 정하고, Razor 는 `_StatusChip` 부분 뷰, JS 는 `App.chip` 이 같은 마크업으로 그린다. Excel·PDF 의 상태 글자도 같은 칩 글자를 쓴다(`ProjectView.StateLabel`). JS 의 휴일 판정은 간트 음영에만 쓴다 — 시트의 근무일 수·휴일 안내는 서버 미리보기(규칙 1)가 준다.
- **편집 창(시트)**: 입력을 바꾼 뒤 바깥·Esc·닫기·취소로 닫으려 하면 "작성 중인 내용을 버릴까요?"로 묻는다. 바깥 클릭은 누른 곳과 뗀 곳이 모두 바깥일 때만 닫는다(입력칸에서 글자를 끌어 선택하다 바깥에서 떼면 닫히던 문제). 긴 입력(진행 내용·사유·메모)은 그 탭의 sessionStorage 에 임시 저장해, 창을 닫거나 새로 고친 뒤 다시 열면 복원을 제안한다(저장하면 지운다). 첫 포커스는 데스크톱만 첫 입력칸에 준다(모바일은 가상 키보드가 내용을 가리므로 시트 자체).
- **다른 사용자의 변경 알림**: 상세 화면은 1분 확인(`/version`)에 이 과제의 마지막 변경 시각(`?handler=Stamp`, `Project.UpdatedAt` 하나만 읽음)을 함께 묻는다. 화면이 가진 것보다 새것이면 "다른 사용자가 이 과제를 바꿨습니다 · 새로 고침" 띠, 과제가 없으면 "삭제됨" 띠를 띄운다. 입력 중일 수 있어 저절로 새로 고치지 않고, 내 저장은 응답의 최신 과제로 시각을 맞추므로 띠가 뜨지 않는다. 그래서 과제를 바꾸는 모든 경로(댓글·체크리스트·첨부 포함)는 `UpdatedAt` 을 갱신한다.
- **시각**: 화면의 시각은 모두 브라우저 현지 시각으로 같은 형식('MM-dd HH:mm', 올해가 아니면 연도를 붙임, `App.time`)이다. 서버가 그리는 시각은 `<time datetime="…Z">` 로 내보내고 스크립트가 바꾼다. 서버가 만드는 시각·날짜(대시보드 기준 시각, Excel·PDF)는 한국 시간이라고 적는다 — 지연 판정이 한국 날짜 기준이기 때문이다.
- **주소**: 상세의 탭은 주소 해시(`#info`·`#files`·`#activity`)로 남아 새로 고치거나 주소를 보내도 같은 탭이 열린다. 작업 바로가기(`#w123`)는 편집 창을 연 뒤 주소에서 지운다(새로 고침에 창이 다시 뜨지 않게). 활동 바로가기(`#a123` — 알림·새 소식에서)는 활동 탭에서 그 활동을 찾아(받아 둔 목록에 없으면 더 오래된 쪽을 이어 받아 1,000건까지) 강조하고, 주소는 그대로 둔다. 목록에서 들어온 상세의 뒤로 단추는 브라우저 뒤로 가기라 목록의 필터·검색이 남는다. 본문 없는 오류 응답(없는 과제 404 등)은 오류 화면으로 다시 그리되, 화면이 JSON 으로 묻는 요청은 JSON 그대로 둔다.
- **인쇄**: 메뉴·도구 모음·탭·알림을 숨기고 A4 가로에 맞춘다. 상세·대시보드는 인쇄 직전 간트를 월 배율로 종이 한 폭에 다시 그리고 끝나면 되돌린다(`App.onPrint`). 의존선은 간트 전체에 걸친 그림 한 장이라 쪽을 나눌 수 없어 인쇄에서 뺀다(위반·임계는 이름 칸 아이콘으로 남는다). 상세·대시보드·내 할 일에 인쇄 단추가 있다(상세는 데스크톱만).
- **오류 번호**: 예기치 않은 서버 오류는 요청 번호(`HttpContext.TraceIdentifier`)를 '오류 번호'로 보인다 — 오류 화면, 화면이 JSON 으로 물은 요청의 500(`{ok:false, error, errorId}`, `JsonErrorMiddleware`), 그리고 5xx 응답의 `X-Error-Id` 머리글(본문이 JSON 이 아니어도 `app.js` 가 안내에 붙인다). 같은 번호가 파일 로그의 `(요청 <번호> <주소>)` 에 남아 관리자가 원인을 찾는다. 내부 예외 메시지는 화면에 보이지 않는다.
- **관리자 알림 칩**: 상단의 칩은 새 버전뿐 아니라 서버 문제를 알린다(`OpsAlerts`, 중요한 것 하나와 나머지 수): 첫 설정 필요(법인이 없어 과제를 등록할 수 없음 — 서버 상태의 첫 설정 점검표로 보낸다), 업데이트 시작 실패·직전 교체 실패(7일 — 시작 실패 안내를 닫으면 그 전의 실패 이력은 다시 알리지 않는다), 자동 확인이 켜져 있고 최근 확인까지 3일 넘게 계속 실패(자동 확인을 끄면 새로 센다 — 끈 서버에 지난 실패 한 번이 영영 남지 않게), 디스크 부족(데이터·첨부·백업 묶음 드라이브 중 하나라도 — 서버 상태·`/health/ready` 와 같은 판정), 백업 실패(2일)·야간 백업을 켰는데 2일 넘게 백업 없음, 10월부터 내년 공휴일 없음. DB·디스크를 읽는 항목은 5분 동안 기억해 화면마다 읽지 않는다(관리 화면에서 법인·공휴일을 고치거나 서버 상태를 열면 바로 다시 읽는다). 일반 사용자에게는 보이지 않는다.
- **입력 부담 줄이기**: 해석·검증은 모두 서버가 하고 화면은 결과 표를 그린다. 날짜 글자는 `InputText.TryDate` 한 곳에서 읽는다(2026-10-12 · 2026.10.12 · 2026/10/12 · 2026년 10월 12일 · 20261012 · 10/12(올해) · Excel 이 붙이는 시각·요일).
  - **작업 여러 개 추가**(상세 단계 카드의 '여러 개 추가', 단계 시트의 '작업 여러 개 추가'): Excel 에서 복사한 줄(작업명 · 담당 · 목표 시작 · 목표 종료[ · 선행 작업명], TAB — 없으면 쉼표)을 붙여넣으면 `?handler=PreviewWorks` 가 줄마다 해석 결과와 문제를 돌려준다. 머리글 줄은 건너뛰고, 둘째 칸이 날짜면 담당 칸을 뺀 것으로 본다. 종료를 비우면 하루짜리, 빈 담당은 '없음', 목록에 없는 담당은 '새로 등록됨'(저장하면 사용자가 생긴다). 문제: 날짜 형식·순서·범위(규칙 16), 사용 중지 담당, 선행 이름(붙여넣은 줄 → 과제의 작업, 같은 이름이 여럿이면 같은 단계, 그래도 여럿이면 문제), 붙여넣은 줄끼리의 순환, 선행 일정('끝나면 시작' — 새 작업 저장과 같은 `EarliestStart`). 확인하면 `AddWorksAsync` 가 다시 검사해 하나라도 틀리면 아무것도 저장하지 않고, 맞으면 SaveChanges 한 번에 작업마다 '작업 추가'·연결마다 '선행 연결 추가'를 BatchId 하나로 남긴다. 미리보기 때 본 단계 버전이 다르면 409. 마지막으로 밀기 계산을 한 번 더 돌려 옮겨야 할 작업이 없는지 확인한다(검사와 저장이 같은 규칙인지 지키는 안전장치). 한 번에 200줄.
  - **저장 후 계속 추가**(새 작업 시트): 저장한 뒤 작업명만 비우고 단계·담당·날짜·선행은 그대로 둔 채 작업명에 포커스한다. 방금 만든 작업도 선행 후보에 넣는다. 제출 단추는 '추가' 하나로 두어 입력칸의 Enter 는 늘 '추가'(저장 후 닫기)다.
  - **복제**: 위치(법인 → 하위 연쇄 선택, 사용 중지 위치는 거절)와 담당(기본: 원본 위치, 나 — 새 이름은 같은 저장에서 사용자로 등록)을 함께 정한다. 작업의 담당은 원본 그대로다.
  - **Excel 가져오기**(`/Projects/Import`, 9장): 양식(`ExcelExporter.ImportTemplate`)의 '과제' 시트는 과제명·유형·법인·위치(법인 아래 경로 '제품군>라인>층')·담당·착수일·협력사·설명·단계 목표일. 단계 목표일은 유형마다 단계가 달라 고정 열 대신 '단계명=날짜; 단계명=날짜' 한 칸에 적는다(유형별 시트보다 틀릴 곳이 적고 과제 한 줄이 한 행으로 남는다). 선택인 '작업' 시트는 과제명·단계명·작업명·담당·목표 시작·목표 종료·선행 작업명이고, 그 과제의 줄이 있으면 템플릿 작업 대신 그 줄로 만든다. '목록' 시트(유형과 단계, 법인, 위치 경로, 사용자 — 유형·법인 칸은 목록에서 고르게 걸어 둔다)와 '안내' 시트를 함께 준다. 열은 머리글 이름으로 찾는다(공백·대소문자 무시).
    - 읽기는 `ProjectImporter`(ClosedXML — 머리글과 줄 글자로만 바꾼다, 날짜 셀은 yyyy-MM-dd. 내용이 있는 줄만 돌고 열은 `MaxColumns` 40까지, 줄 상한을 넘으면 칸은 더 읽지 않고 줄 수만 센다 — 먼 칸 하나만 채운 작은 파일로 서버를 붙잡지 못하게)이고, 검사·등록은 `ProjectService.PreviewImportAsync`/`ImportAsync` 다. 과제 한 줄은 등록 화면과 같은 `BuildProjectAsync`(저장하지 않는 등록 — 같은 검증·목표일 설정 기록·템플릿 작업), 작업 줄은 붙여넣기와 같은 검사·적용을 거친다. 담당자는 `UserService.ResolveAsync`(저장 안 함 — 정확히 같은 이름을 먼저, 없으면 대소문자를 무시해 찾는다. 두 DB 의 비교 규칙이 달라도 결과가 같게, 미리보기의 '새 담당자' 판정도 같은 규칙) 규칙을 따르고, 목록에 없는 이름은 '새로 만들 담당자 n명'으로 보여 `confirmNewUsers` 확인을 받아야 가져온다(오타로 사용자가 생기지 않게).
    - 미리보기는 행·열 단위 문제(시트·행·열 이름·문구)를 돌려준다. 같은 과제명이 두 번이면 문제다(작업 시트가 과제명으로 찾는다). 가져오기는 같은 검사를 처음부터 다시 하고 문제가 하나라도 있으면 아무것도 저장하지 않으며, 모든 과제·작업·새 사용자를 SaveChanges 한 번에 저장한다. 과제마다 '과제 등록 (Excel 가져오기: 파일명)' 활동을 남긴다. 서버는 올린 파일을 보관하지 않는다 — 화면이 같은 파일을 미리보기·가져오기에 두 번 보낸다. 상한: 파일 5MB(.xlsx 만), 과제 200줄, 작업 2000줄. 기기·용기 내역은 가져오지 않는다(등록 뒤 수정 화면에서 넣는다).
  - 문제 있는 줄은 기존 오류 모양(`form-error` — 줄 아래에 칸 이름과 문구)으로 보인다. 지연 칩(빨강)과 헷갈리지 않게 칩을 쓰지 않는다. 좁은 화면에서는 표를 줄마다 이름표를 붙인 카드로 쌓는다(`.rows-table`).
- 접근성: 상세 간트의 이름 칸은 단추라 키보드로 편집 창을 연다. 저장할 때마다 다시 그리는 요약에는 aria-live 를 두지 않고 결과는 토스트(#toasts)가 읽어 준다. 하단 탭은 지금 화면에 aria-current 를 단다.
- **상황판**(`/Board`, `BoardService`): 화면 높이 하나에 모두 담는다(스크롤 없이). 목록이 칸을 넘치면 `board.js` 가 행 위치로 쪽을 나눠 12초마다 넘긴다(쪽 번호 표시). 좁은 화면에서는 한 화면 맞춤을 풀고 세로로 쌓는다. **자동 갱신**: 1분마다 `?handler=Stamp`(데이터 버전 + 한국 날짜 + 빌드)만 묻고 바뀌었을 때만 같은 주소를 다시 받아 `#board` 만 바꾼다(빌드가 바뀌면 페이지 전체). 연결이 끊기면 마지막 화면을 두고 '연결할 수 없음'을 띄운다. **데이터 버전**(`DataVersion`, 싱글턴 — 서버 한 대 운영이라 프로세스 안 값): `AppDb.SaveChangesAsync` 한 곳에서 과제 그래프(Project·Stage·WorkItem·CheckItem·WorkLink·StageLink·Attachment·Activity)가 추가·수정·삭제된 저장이 성공했을 때만 올린다. 마지막 접속 시각·방문·관심·알림 읽음·기준 정보는 세지 않는다. 시작 값은 시각이라 서버를 다시 띄우면 한 번 다시 받는다. 날짜가 바뀌면 데이터가 그대로여도 지연 판정이 달라지므로 확인값에 날짜를 넣는다. 정체·위험 판정은 하루 중에도 서버 시각으로 바뀌므로 데이터가 그대로여도 30분이 지나면 다시 받는다. 머리의 시각은 '반영'(화면을 그린 시각)과 '확인'(Stamp 응답에 실린 서버 한국 시각 — 바뀐 것이 없는 날에도 화면이 살아 있음을 보인다)으로 나눠 적는다. **이름 등록 없이** 열린다(사람 없이 켜 두는 PC) — `UserGateMiddleware` 가 `/Board` 의 GET 만 통과시키고(허용 대역 검사는 그대로) 사용자를 만들지 않으므로 담당자 목록·첫 관리자 판정에 닿지 않는다. 메뉴의 '상황판'은 새 창으로 연다.
- **첫 화면 안내**: 과제가 하나도 없을 때(휴지통 제외) 대시보드 맨 위에 안내 카드를 둔다. 사용 중인 법인이 없으면 등록 화면이 막다른 길이므로(위치 선택이 비어 저장할 수 없다) 관리자에게는 '관리 > 계층'과 첫 설정 점검표(`/Admin/Status`)로, 일반 사용자에게는 '관리자에게 기준 정보 등록을 요청하세요'로 안내한다(`_SetupNeeded`). 등록 화면도 법인이 없으면 같은 안내를 맨 위에 띄운다. 법인이 있으면 '과제 등록'과 도움말로 보낸다.

### 4.1 활동·새 소식·알림

과제를 직접 찾아가지 않아도 내 일과 관계된 변경을 알게 한다. 판정은 서버 한 곳(`Rules.NewSince`·`IsNewActivity`·`CanEditComment`, `ActivityLog`)에 두고 화면은 서버가 준 값을 그린다.

- **활동 탭**: 종류 칩은 변경 이력 화면과 같은 분류(`Reporting.Kinds` — 일정 변경·진행(완료·체크)·댓글·등록·상태·구성 변경·첨부)를 쓰고, `ActivityView.Kind` 로 서버가 정한다. 종류·단계 조건은 DB 에서(`KindIs`, `StageId` 같음), 글자 검색(내용·사유·사람)은 그 과제의 활동을 투영한 뒤 메모리에서 한다. 조건이 있으면 `?handler=Activities&kind=&stageId=&q=` 로 그 조건의 목록을 따로 나눠 받고('더 보기'도 같은 조건), 조건을 풀면 쌓아 둔 최근 목록으로 돌아간다. 시각은 `App.time`(올해가 아니면 연도).
- **새 활동**: 사용자가 상세를 연 시각을 `ProjectVisit` 에 남긴다(요청 하나에 저장 한 번 — 목록·대시보드·1분 확인은 방문으로 치지 않는다). '새 활동'은 **다른 사람이** 마지막 방문 뒤에 남긴 활동이고, 오래 안 본 과제가 수백 건으로 보이지 않게 최근 `Rules.NewActivityDays`(7)일까지만 센다(처음 보는 과제는 7일). 댓글 수정·삭제 기록은 그 댓글로 보이므로 세지 않는다. 상세는 연 순간의 기준(`seen.since`)으로 새 활동에 표시(`ActivityView.New`)를 하고 새 활동과 지난번에 본 활동 사이에 '여기부터 위가 새 활동입니다' 구분선을 그린다. '더 보기'는 같은 기준을 서버에 보내 표시를 이어 받는다. 과제 목록·대시보드(지연 과제·다가오는 일정)의 '새 활동 n' 은 과제마다 묻지 않고 한 번의 그룹 쿼리(`ProjectService.NewCountsAsync` — `At` 색인으로 최근 7일 활동만 읽고 내 방문 기록을 왼쪽 조인, 과제별 `COUNT`)로 센다. 6장의 '그룹 집계는 하지 않는다'의 예외다 — 과제별로 활동을 읽어 오면 목록 한 번에 과제 수만큼 쿼리가 든다.
- **새 소식(내 할 일 맨 위)**: 내 과제(담당)·관심 과제·내 작업(담당·부담당)·나를 알릴 사람으로 고른 댓글에 다른 사람이 남긴 활동 중 그 과제를 마지막으로 본 뒤(최근 7일)의 것, 최근 30건. 자동 밀기·연쇄 이동으로 내 작업 일정이 바뀐 기록은 그 작업의 활동이라 함께 나온다. 조건은 EXISTS(`Any`)로 DB 에서 거르고 과제별 방문 시각 비교는 메모리에서 한다. 누르면 상세의 그 활동(`#a{id}`)으로 가고, 그 과제를 열면 사라진다.
- **관심 과제**: 상세 머리·과제 목록·내 할 일의 별(`aria-pressed`). 관심 과제는 새 소식과 알림의 대상이다. 방문·관심·읽음은 개인 설정이라 과제 활동을 남기지 않는다.
- **알림 만들기**: 활동은 모두 `ActivityLog.New` 한 곳에서 만든다(`ProjectService.NewActivity`, 첨부 올리기·삭제). 만든 활동은 기억해 두었다가 저장 직전(`AppDb.SaveChangesAsync` 의 저장 훅 — 어느 서비스가 저장하든 빠지지 않게) 받을 사람을 계산해 **같은 SaveChanges** 로 알림을 더한다. 받을 사람: (a) 활동이 가리키는 작업의 담당·부담당(자동 밀기·연쇄 이동 포함 — 저장 전 값으로 찾고, 새 작업·지운 작업·새로 맡은 사람은 서비스가 따로 더한다), (b) 과제 담당(새로 맡은 담당 포함), (c) 관심 등록자, (d) 멘션. 활동을 남긴 본인과 사용 중지된 사람은 빼고, 댓글 수정·삭제 기록은 새로 고른 멘션에게만 알린다. 한 저장에서 한 사람에게는 **과제마다 한 건**이다 — 가장 직접적인 이유(멘션 > 내 작업 > 내 과제 > 관심 과제)와 대표 활동 하나를 남기고 함께 남은 활동은 '외 n건'으로 센다(작업 하나를 옮겨 후행 열 개가 밀려도 한 건). 새 과제의 활동처럼 저장 전에 과제 Id 를 모르는 것은 저장 뒤 한 번 더 저장한다. `Key` 는 같은 사건을 두 번 알리지 않는 열쇠다: 새 활동은 '저장·과제·사람', 이미 있는 활동을 가리키는 알림(고친 댓글의 새 멘션)은 '활동·사람' — 멘션을 뺐다가 다시 골라도 또 알리지 않는다.
- **알림 보기**: 헤더의 종에 읽지 않은 수를 보인다. 화면을 그릴 때 세지 않고(_Layout 의 모든 요청에 알림 조회를 붙이지 않게) 가벼운 별도 요청 `/api/unread`(사용자 조회 + `(UserId, ReadAt)` 색인 `COUNT`)를 처음 한 번과 1분 버전 확인(`App.onPoll` — 보이는 탭만)에 얹어 묻는다. `/version` 은 사용자를 찾지 않으므로 거기에 싣지 않는다. 배경 요청(`X-Background`)이라 자동 업데이트의 '사용 중'으로 치지 않는다. 알림 목록(`/My/Notifications`)의 항목을 누르면 `?handler=Go` 가 읽음으로 바꾸고 상세의 그 활동으로 보낸다(스크립트 없이도 읽음 처리가 빠지지 않게).
- **댓글 고치기·지우기**: 작성자만, 남긴 뒤 `Comments:EditHours`(기본 24)시간 안에(`Rules.CanEditComment` — 서비스의 검사와 화면 단추가 같은 판정). 고치면 첫 원문을 `OldValue` 에 한 번만 남기고 `EditedAt` 을 적어 '(수정됨)'으로 보인다. 지우면 본문을 '삭제된 댓글'로 바꾸고 원문·멘션도 지운다(내용을 지우려는 것이므로). 그 댓글을 가리키던 알림의 글도 바꾼다. 행은 지우지 않아 이력의 자리와 순서가 남고, 둘 다 '댓글 수정'·'댓글 삭제' 활동(`CommentChanged`, `NewValue` = 댓글 활동 Id — 화면의 '해당 댓글 보기')으로 누가·언제를 남긴다. 주간 보고의 진행 내용에서 지운 댓글은 빠진다.
- **멘션**: 댓글 입력에서 '@' 를 치면 '알릴 사람' 칸으로 옮겨 목록(datalist)에서 고른다. 이름에 공백이 있을 수 있어 본문을 파싱하지 않고, 고른 사람의 Id 목록을 댓글과 함께 보내 `ActivityMention` 에 남긴다(본문의 '@이름'은 읽는 사람을 위한 글자일 뿐). 없는 사용자·사용 중지된 사용자는 `RuleException`(field `mentions`)이고, 담당자 지정과 달리 새 사용자를 만들지 않는다. 한 댓글에 20명까지. 활동 목록은 칩으로 보인다.
- **메일 요약**(`Services/Notify.cs`): `Notify:Enabled`(기본 꺼짐)이면 `NotifyWorker`(BackgroundService, `IServiceScopeFactory` 로 범위를 만들고 지금 사용자 없이 동작 — 활동을 남기지 않는다)가 1분마다 때를 보고, 한국 시간 `Notify:DailyHour`(기본 8)시부터 4시간 안, **근무일**에 하루 한 번 보낸다(주말·공휴일의 알림은 다음 근무일 요약에 모인다. 오후에 다시 시작한 서버가 그날 요약을 늦게 보내지 않는다). 보낸 날짜는 `App_Data/notify.json`(`Notify:StatePath`)에 남겨 다시 시작해도 같은 날 두 번 보내지 않는다. 사용자별 한 통: 읽지 않았고 아직 메일로 보내지 않은 알림(최근 30건) + 내 작업의 지연·임박(`Reporting.My` — 내 할 일과 같은 판정). 보낸 알림은 `EmailedAt` 을 적어 다음 요약에 다시 싣지 않고, 실패하면 로그와 서버 상태(`OpsChecks` '메일 요약')에 남기고 그 알림은 다음 요약에 다시 싣는다. 통로는 `INotifyChannel` 로 나눴고 사내 SMTP(`System.Net.Mail`) 하나만 있다(메신저 웹훅은 만들지 않는다). 받는 주소(`AppUser.Email`)는 **관리자만** 관리 > 사용자에서 정한다 — IP 로 식별하므로 본인이 입력하게 하면 남의 알림을 가로채도록 바꿀 수 있다. 같은 시트의 '시험 메일'은 요약을 꺼 둔 서버에서도 메일 서버 설정을 확인한다.
- 화면 점검(e2e)은 다른 사람의 활동을 만들기 위해 두 번째 브라우저가 `X-Forwarded-For` 로 다른 PC 를 흉내 낸다. 그래서 개발 환경 설정(`appsettings.Development.json`)은 `TrustForwardedHeaders` 를 켠다 — 같은 서버(루프백)의 프록시 머리글만 믿으므로 개발 PC 밖에서는 흉내 낼 수 없다.

## 5. 사용자 식별과 권한

로그인이 없다. 접속 IP 로 사용자를 찾고, 처음 보는 IP 는 이름을 등록하게 한다. 같은 이름으로 다시 등록하면 그 IP 가 기존 사용자에 추가로 연결된다(PC 교체·IP 변경 대응). 사내망에서 서로 신뢰한다는 전제이며 다른 사람 이름을 입력하는 것을 막지 않는다. 쿠키 식별·열람자 역할은 두지 않는다.

이 전제는 앱 데이터(과제·일정) 범위의 것이다. 관리자는 업데이트 파일을 올려 서버에서 실행할 수 있으므로, **이름 입력만으로 관리자 권한을 얻는 길**은 막는다.

- **관리자 예외**: 이름 등록·사용자 바꾸기에서 관리자 이름은 이미 그 관리자에 연결된 IP 에서만 받는다. 새 PC 를 쓰게 된 관리자는 다른 관리자가 관리 > 사용자에서 IP 를 추가하거나, 서버 콘솔에서 `GanttScheduler.exe admin <이름> [--ip <주소>]` 로 연결한다(관리자가 혼자이거나 아무도 없을 때의 복구 경로. 웹 서버와 같은 설정으로 DB 를 열고, 마이그레이션은 하지 않으며 구조가 맞지 않으면 안내하고 끝낸다).
- **첫 관리자**: 관리자가 한 명도 없으면 서버 자신(루프백)에서 등록한 사람이 관리자가 된다(`Access:FirstAdminLocalOnly`, 기본 켬). 설치 직후 사내망의 아무 PC 가 먼저 등록해 관리자를 선점하지 못하게 한다. 다른 PC 에서 등록하면 일반 사용자가 되고, 관리 화면에 "서버에서 접속하거나 admin 명령을 쓰라"는 안내가 뜬다.
- **사용자 바꾸기**: 헤더의 내 이름을 누르면 이 기기를 다른 이름으로 다시 연결한다(공용 PC, IP 를 넘겨받은 경우). 이미 아는 IP 의 등록 요청은 이 화면에서 온 것(`switch` 표시)만 받는다. 같은 이름을 입력하면 그 사람에 연결된다는 점(동명이인·오타)을 화면에 적는다. 관리자에 연결된 기기를 다른 이름으로 옮기면 관리자 예외 때문에 그 관리자는 이 기기에서 돌아올 수 없으므로, 되돌리는 방법(다른 관리자의 IP 연결, 관리자가 혼자면 admin 명령)을 보여 주고 확인란을 고른 경우에만 옮긴다. 막지는 않는다 — IP 를 넘겨받은 사람은 자기 이름으로 바꿀 수 있어야 한다.
- **IP 재확인**: IP 연결을 `Access:ReconfirmDays`(기본 30)일 넘게 쓰지 않았으면 "OOO 님이 맞습니까?"를 묻는다. 맞다고 하면 그대로 쓰고, 아니면 사용자 바꾸기로 간다. DHCP 로 IP 가 다른 사람에게 넘어갔을 때 조용히 이전 사람으로 기록되지 않게 하기 위해서다. 마지막 접속 시각은 하루에 한 번만 갱신한다. **관리자 계정은 "맞습니다"로 되살리지 않는다**(서버 자신 제외) — IP 를 넘겨받은 사람이 클릭 한 번에 관리자 권한을 얻게 되기 때문이다. 본인이면 다른 관리자가 관리 > 사용자에서 그 IP 를 다시 연결하거나(이미 연결된 IP 를 다시 연결하면 마지막 접속이 갱신된다) admin 명령을 쓴다. 30일 안에 IP 가 넘어간 경우는 이 확인으로도 막지 못한다(로그인 없는 설계의 남은 위험).
- **접속 허용 대역**: `Access:AllowedNetworks`(CIDR 목록)를 두면 그 밖에서 온 요청은 이름 등록 화면도 없이 403 으로 거절한다. 비어 있으면 모두 받고, 서버 자신(루프백)은 항상 받는다. 방화벽 규칙도 설치 명령의 `--remoteip` 로 같은 대역만 열 수 있다(방화벽의 `LocalSubnet` 은 앱 설정에 쓸 수 없어 실제 대역을 적는다).
- **IP 형식**: 관리 화면의 IP 연결, admin 명령의 `--ip`, 허용 대역, `--remoteip` 는 IPv4 를 앞자리 0 없는 십진수 네 마디로만 받는다. `IPAddress.TryParse` 는 `10` 을 0.0.0.10 으로, 앞자리 0 을 8진수(`192.168.001.010` → 192.168.1.8)로 읽어 엉뚱한 PC 를 관리자에 연결하거나 엉뚱한 대역을 열 수 있기 때문이다(`AccessOptions.TryParseIp`).
- **IP 관리**: 관리 > 사용자에서 사용자별 접속 IP 와 마지막 접속일을 보고, IP 를 직접 연결·해제한다. 지금 쓰고 있는 기기의 IP 는 해제할 수 없다(스스로 잠기지 않게).
- **담당자 이름**: 목록에 없는 이름은 IP 없는 담당자로 만든다(나중에 그 이름으로 등록하면 연결). 저장에 실패하면(동시 수정·사유 누락 등) 만들지 않는다 — 새 사용자를 요청의 마지막 저장에서 함께 저장한다. 사용 중지된 이름은 새로 지정할 수 없다(이미 지정된 것은 그대로 둘 수 있다). 화면은 목록에 없는 이름을 입력하면 "새 담당자로 등록됩니다"라고 알린다.
- **과제 삭제 = 휴지통**: 과제를 지우면(담당자·등록자·관리자, 화면이 본 과제 버전 확인) 행을 지우지 않고 `DeletedAt`·지운 사람·사유(선택)만 적고 '과제 삭제' 활동(`ProjectDeleted`)을 남긴다. 단계·작업·첨부 파일·활동·방문·관심·알림·과제 간 연결은 그대로 둔다(복원하면 그대로 돌아온다). 지운 과제는 **모든 조회에서 뺀다** — 전역 필터(HasQueryFilter)는 섀도 빌드의 가짜 EF 에 없어 `AppDb.LiveProjects`·`LiveActivities` 한 곳을 거친다: 과제 그래프(Graph·AllAsync·RequireAsync·LoadInfo·Stamp·미리보기), 목록·대시보드, 내 할 일, 주간 보고·리드타임·변경 이력, 첨부 내려받기·올리기, 복제 원본, 새 소식·새 활동 수·관심 과제, 알림(목록·읽지 않은 수·메일 요약 — `ProjectId` 가 FK 가 아니라 EXISTS 로 거른다), 과제 간 연결(연결은 남기되 화면·위반 계산에서 빼고 새로 잇지 않는다), 연결 상대 검색, 관리의 공휴일 영향·리드타임 힌트. 휴지통·영구 삭제·기준선 이전만 `Projects` 를 그대로 읽는다. 앞으로 과제·활동을 읽는 새 조회(스냅샷 등)도 이 둘을 거친다.
- **관리 > 휴지통**(관리자만): 지운 과제 목록(지운 사람·시각·사유·자동 영구 삭제 예정일), 복원(`ProjectRestored` 활동 — 서비스는 지울 권한이 있는 사람에게 허락하지만 화면은 관리 화면에만 둔다), 바로 영구 삭제(되돌릴 수 없어 관리자만), 최근 영구 삭제 기록. 복원·영구 삭제는 화면이 본 과제 버전을 보낸다 — 그 사이 다른 사람이 복원·수정한 뒤 다시 지운 과제(관리자가 본 적 없는 삭제 건)는 409 로 새로고침을 안내한다. 좁은 화면에서는 기록 표를 행 목록으로 쌓는다. 영구 삭제는 예전 과제 삭제 그대로 의존 관계·과제 간 연결(상대 과제에 '(과제 삭제)' 기록)을 먼저 지우고 나머지는 DB cascade 에 맡긴 뒤 첨부 폴더를 지운다(못 지우면 경고 로그 — 고아 파일 정리가 치운다). 활동까지 사라지므로 `DeletedProjectLog` 한 줄과 파일 로그 경고 한 줄을 남긴다.
- **자동 정리**(`TrashWorker`): 서버가 뜬 뒤 5분, 그 뒤 하루마다 `Trash:KeepDays`(기본 30)일이 지난 과제를 영구 삭제한다. 0 이하면 끈다. 배경 작업에는 현재 사용자가 없어 과제마다 범위를 새로 만들고 **그 과제를 지운 사람**을 행위자로 둔다(상대 과제에 남는 연결 해제 기록의 주인). 정리 기록의 영구 삭제자는 '자동 정리(보관 기간 경과)'. 한 과제가 실패해도 나머지는 계속하고 다음 날 다시 시도한다.
- **사용자 합치기**(관리 > 사용자 시트의 '다른 사용자로 합치기', `UserAdminService.MergeAsync`, 관리자만): 이름 오타로 같은 사람이 둘이 된 경우 from 을 into 로 합친다. 한 번의 SaveChanges 로 AppUser 를 가리키는 **모든** 행을 옮긴다 — 목록은 `UserAdminService.References` 한 곳이고, 시험이 EF 모델의 사용자 FK 와 FK 없는 사용자 열(`ProjectSnapshot.OwnerId` 등)을 기계적으로 찾아 이 목록과 같은지, 병합 뒤 from 을 가리키는 행이 0 인지 본다(새 참조를 더하면 목록과 병합에 함께 더한다). 휴지통 과제도 옮긴다. 유일 색인이 있는 개인 행(방문·관심·멘션)이 겹치면 into 쪽 하나로 합친다(방문은 늦은 시각, 관심은 이른 시각). 작업의 담당과 부담당이 같아지면 부담당을 비운다. 담당이 바뀐 과제·작업은 `Version` 을 올리고, 바뀐 과제마다 '사용자 병합: A → B' 활동(사유, 같은 BatchId)을 남긴다. 관리자 권한은 합집합, 메일·소속은 into 에 없을 때만 가져온다. **from 은 지운다**(사용 중지 + 이름 변경 대신) — 이름이 유일해서 남겨 두면 오타 이름이 담당 입력·자동완성에 계속 나오고, 기록은 모두 into 로 옮겨 지워도 잃는 것이 없다. 같은 저장에서 from 에게 갈 알림은 into 로 보낸다(`ActivityLog.Redirect`). 지금 화면을 쓰는 사용자는 from 이 될 수 없다. 사용 중인 from 을 사용 중지된 into 로 합치지 않는다(IP 가 사용 중지된 사용자에게 붙어 이름 등록 화면으로 밀려나고 옮긴 담당의 알림이 끊긴다 — 먼저 into 를 다시 사용으로 바꾼다. 둘 다 사용 중지면 허용). 시트의 고르기 목록도 같은 기준이다.
- **담당 이관 후 사용 중지**(`ReassignAsync`): 사용자 목록에 '과제 n · 작업 n'(진행·보류 과제 담당, 단계가 끝나지 않은 미완료 작업의 담당·부담당 — 휴지통 제외)과 마지막 접속일을 보인다. 맡은 일이 있는 사람의 '사용 중지'는 이관 시트를 연다: 넘겨받을 사람(사용 중인 사람만)과 범위(진행 과제 담당·미완료 작업)를 고르고, 과제·작업마다 활동(한 BatchId)·`Version`++·받는 사람 알림을 남긴 뒤 사용 중지한다. 완료·중단 과제와 끝난 작업의 담당은 기록으로 그대로 둔다. 맡은 일이 없으면 바로 사용 중지한다. 이 판단은 서버도 한다 — 관리 화면의 사용 중지(`MasterService.Toggle`)는 맡은 일이 있으면 거절하므로(오래된 화면·직접 요청) 이관은 `ReassignAsync` 로만 한다. 이관 시트에서 범위를 끄고 넘기면 남은 수를 변경 이력에 '넘기지 않음 — 과제 n · 작업 n 남음'으로 적는다.
- **관리 변경 이력**(`MasterChange`, `Services/MasterChanges.cs` 의 `MasterLog`): 공휴일·해상 운송일·유형/단계/작업 템플릿·관리자 지정처럼 일정 계산과 권한을 바꾸는 변경은 과제 활동에 담을 곳이 없어 따로 남긴다. 기준 정보의 추가·수정(바뀐 칸만, 이전 값 → 새 값)·사용 중지/다시 사용·삭제·순서 이동, 공휴일 붙여넣기(한 줄), 사용자 등록(이름 등록 화면 — 행위자는 본인)·담당 입력으로 생긴 사용자·IP 연결/해제·관리자 지정/해제·합치기·이관, admin 명령(행위자 없음 = 서버), IP 보존 정리(서버), 업데이트 설정 변경·적용·되돌리기·배포 파일 올리기·지금 백업. 변경과 **같은 SaveChanges**(저장 훅)로 저장해 변경만 되고 이력이 빠지는 일이 없다. 새 항목의 Id 는 저장 때 채운다. 이력은 추가만 한다. 관리 > 변경 이력 탭(관리자만)에서 종류·기간·사람(서버 포함)으로 걸러 50줄씩 본다. 바꾼 것이 없는 저장은 남기지 않는다.
- **사용 수**: 기준 정보 목록에 그 항목을 쓰는 과제 수(휴지통 제외)를 보인다 — 계층은 하위 위치의 과제를 상위로 올려 세고, 기기 대분류는 하위 타입을 쓰는 과제까지 한 번씩, 조직은 사용 중인 사용자 수, 지연 사유는 기록 수. 종류마다 GroupBy 한 번이다.
- **사용 현황**(관리 > 사용 현황, 누구나): 최근 30일(`Rules.UsageDays`) 조직별 사용자 수·접속자 수(IP 연결의 `LastSeenAt`)·갱신 건수(활동)·30일 동안 갱신 없는 진행 과제 비율. 조직 줄과 사람 줄의 '진행 과제'는 같은 규칙(`Rules.IsUsageProject` — 진행만, 보류 제외)으로 세어 합이 맞는다(사용자 목록의 '과제 n'은 이관 범위라 진행·보류). 개인 감시가 아니라 조직 집계를 먼저 보인다 — 사람별 마지막 접속·갱신 수는 관리자에게만 준다. 마지막 접속은 하루 한 번 갱신하는 값이라 날짜 단위다.
- **보존**: IP 연결은 `Access:AddressKeepDays`(기본 365)일 넘게 보이지 않으면 하루 한 번 지운다(`AddressRetentionWorker`, 0 이하면 끔). 퇴사자·반납 PC 의 IP 가 다음 사람에게 넘어가 엉뚱한 이름으로 기록되는 것을 줄인다. 지운 연결마다 관리 변경 이력에 남긴다. 첨부는 자료 탭에 과제의 첨부 합계를 보이고, `Storage:ProjectMaxMB`(기본 없음)를 정하면 과제 합계가 넘는 올리기를 거절한다(남은 여유를 알린다).
- 기준 정보 변경은 관리자만, 과제 삭제는 담당자·등록자·관리자만, 첨부 삭제는 올린 사람·과제 담당자·관리자만, 댓글 고치기·지우기는 작성자만(정한 시간 안), 메일 요약 받는 주소는 관리자만 정한다(관리 화면에서만 보인다). 그 외 편집은 등록한 사용자 누구나. 삭제 단추는 지울 수 있는 사람에게만 보인다 — 서버가 같은 판정(`Rules.CanDeleteProject`·`CanDeleteAttachment`)으로 `ProjectView.CanDelete`·`AttachmentView.CanDelete` 를 채운다.
- 리버스 프록시 뒤에 둘 때는 `TrustForwardedHeaders: true` 로 실제 접속 IP(X-Forwarded-For)를 쓴다. 이 값은 같은 서버(루프백)의 프록시가 보낸 것만 믿는다. 같은 서버의 프록시를 이 설정 없이 쓰면 모든 요청이 루프백으로 보여 식별·허용 대역·첫 관리자 규칙이 모두 무력해진다.
- 모든 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: same-origin` 을 붙인다. 첨부 미리보기는 같은 출처의 틀(iframe)이라 그대로 된다.
- 사용자 조회(UserGate)는 `/version`·`/health…`·정적 파일 뒤에 둔다. 열린 화면이 1분마다 묻는 `/version` 에 DB 를 읽지 않고, DB 가 멈춰도 상태 확인은 답하게 하기 위해서다. 감시 도구용 `/health/ready` 는 DB 왕복과 디스크 여유를 보고 실패하면 503 을 준다. 누구나 부를 수 있어 항목 이름과 수준만 주고 원인 문구는 서버 상태 화면(관리자)에만 보인다.
- 서버 상태 화면과 진단 정보·로그 내려받기는 관리자 전용이다(경로·DB 서버 이름이 보인다). 연결 문자열은 서버·DB 이름만 보이고, 진단·로그 파일의 `Password=`·`User Id=` 값은 가린다(`Redact`). 백업 설정·목록도 관리자에게만 내려준다.

## 6. DB

| | 용도 | 스키마 관리 |
|---|---|---|
| SQL Server | 운영 | EF 마이그레이션 — 앱 시작 시 자동 적용. 테이블은 `pm` 스키마. 일시적인 연결 끊김은 EF 재시도 전략(`EnableRetryOnFailure`)으로 다시 시도한다 |
| SQLite | 미리보기·개발·테스트 | 파일이 없으면 그때 새로 만든다(`EnsureCreated`). 모델이 바뀌면(스키마 해시 비교) 새로 만든다 — 개발 환경은 지우고, 그 밖에서는 지우지 않고 `gantt.db.<시각>.bak` 으로 옮겨 둔다 |

마이그레이션은 SQL Server 기준 한 벌만 관리한다. SQLite DB 는 버려도 되는 데이터만 담는다는 전제다. 그래도 운영 설정으로 SQLite 를 쓰는 서버가 있을 수 있어, 개발 환경이 아니면 구조가 바뀌어도 기존 파일을 남긴다(옮기지 못하면 지우지 않고 시작을 멈춘다).

스키마 해시는 EF 가 만든 생성 스크립트의 해시라 EF 패치 버전만 바뀌어도 달라질 수 있다. 패키지 버전은 `Directory.Packages.props` 에 정확한 값으로 고정하고(`packages.lock.json`, CI 는 잠금 모드 복원), 올리는 일은 Dependabot PR 로만 한다.

코드에서 트랜잭션을 직접 열지 않는다(`SaveChanges` 한 번이 트랜잭션 하나). 재시도 전략과 함께 직접 트랜잭션을 쓰려면 `Database.CreateExecutionStrategy()` 안에서 열어야 한다.

조회는 과제 전체를 단계·작업까지 읽어 메모리에서 집계한다. 과제 수백 건 규모에서는 충분하고, 두 DB 의 쿼리 번역 차이를 피할 수 있다. 과제가 수천 건을 넘으면 대시보드·목록 쿼리를 DB 집계로 바꿔야 한다. 그 안에서 요청당 낭비는 줄인다:

- **DB 로 옮기는 조건은 두 DB 에서 똑같이 번역되는 단순한 것만**: 상태·유형·법인 같음, 기간 안 활동 존재(`Any`), 사용자 Id, 활동 유형 같음(`Reporting.KindIs` — 종류를 `KindOf` 로 유형 전부에 대해 역매핑해 `유형 = A OR 유형 = B …` 식을 만든다. 목록 매개 변수(`IN`·`OPENJSON`)는 SQL Server 호환 수준에 따라 번역이 달라 쓰지 않는다). 판정 규칙(지연·임박 등)과 글자 검색(SQLite 는 대소문자 구분, SQL Server 는 정렬 규칙 — 결과가 다르다)은 필요한 열만 읽은 뒤 메모리에서 한다. 그룹 집계·요약 컬럼 저장은 하지 않는다(계산 값을 저장하지 않는 원칙, 2장 3).
  - 목록: 상태 탭·유형·법인은 DB 에서(지연·위험·정체 탭은 진행 과제만 읽고 판정은 메모리에서). 검색은 과제 엔티티(협력사·작업 담당 이름 포함 — 이미 읽은 그래프)를 메모리에서 본다.
  - **조기 경보 판정 범위**: 대시보드·목록·주간 보고는 원래 단계·작업까지 읽으므로 위험 판정에 필요한 것은 작업 의존(`AllAsync(withLinks: true)` — 분할 쿼리 하나)·근무일 달력(요청 안에서 한 번)·과제 간 연결이다. 과제 간 연결은 과제 수백 건의 단계 Id 를 조건으로 넘기지 않고 연결 표 전체를 양쪽 단계·과제와 조인해 한 번에 읽는다(`AllCrossLinksAsync` — 목록 매개 변수 없음, 연결은 과제보다 훨씬 적다). 그래서 상세와 같은 전진 계산·연결 위반으로 판정한다. 최근 사유는 카드에 보이는 과제 Id 로 한 번 읽고(`RecentNotesAsync`) 과제별 고르기는 메모리에서 한다 — 목록 매개 변수(`IN`)의 예외라 길이에 상한을 둔다: 위험 카드는 보이는 `RiskShown`(8)건, 지연 카드는 지연 큰 순 앞의 `NotesMax`(40)건(그 뒤 행은 사유 줄 없이 보인다). 대시보드 DB 명령 상한을 10 → 14 로 올렸다(`DataAccessHttpTests`). 내 할 일: 진행 과제만. 리드타임: 작업 없이 단계만, 중단 과제 제외. 주간 보고: 진행 과제 + 그 주에 활동이 있는 과제(보고에 오르는 과제가 그것뿐이다).
  - 변경 이력: 기간·과제·사용자·종류 조건과 건수·정렬(`At`, `Id` 내림차순)·쪽 나누기를 DB 에서, 열은 과제명만 투영한다. 글자 검색이 있으면 조건에 맞는 행을 투영해 메모리에서 거르고 나눈다. 사용자가 크기를 정하는 조회라 여러 과제의 기간은 1년(`InsightService.HistoryMaxYears`)까지로 맞추고 안내한다. 과제 하나(`projectId`)는 행 수가 그 과제의 활동으로 묶이므로 상한이 없고, 기간을 비우면 그 과제의 첫 활동부터 본다.
- **변경은 필요한 그래프만 추적해 읽는다**(`ProjectService.LoadForChangeAsync`): 단계 → 작업·체크리스트, 의존 관계. 과제 정보 수정·복제만 유형·기기·용기 내역을 더 읽는다. 활동은 읽지 않은 컬렉션에 더해도 저장할 때 INSERT 된다. 댓글은 과제 행만 읽는다. 과제 영구 삭제(휴지통 — 5장)는 과제 행과 의존 관계만 읽어 의존 관계를 먼저 지우고(같은 SaveChanges 안에서 과제 행보다 앞서 — SQL Server 는 한 문장 안의 cascade 와 NO ACTION 검사 순서가 얽힐 수 있다) 나머지(단계·작업·체크·첨부·활동)는 DB cascade 에 맡긴다. 과제 간 단계 연결(`StageLink`, Restrict)이 걸린 단계가 있으면 그 단계만 작업과 함께 추적해 읽는다 — EF 는 추적하는 행 사이의 FK 로만 지우는 순서를 정하므로, 단계를 모르면 과제 행을 연결보다 먼저 지워 DB cascade 가 Restrict 에 걸린다(연결 → 작업 → 단계 → 과제 순서가 되게).
- **화면 데이터는 추적하지 않고 새로 읽는다**: 상세(`ViewAsync`)는 변경 응답에서도 `AsNoTracking` 으로 다시 읽어 저장된 값을 보인다. 활동은 그래프에 싣지 않고 건수·목표일 변경 횟수는 `COUNT`, 최근 활동은 필요한 열만 읽는다. 과제 하나의 활동을 최근 순으로 자르는 조회(상세·'더 보기'·과제 조건 변경 이력)를 위해 활동에 `(ProjectId, At)` 인덱스를 둔다(과제 FK 인덱스를 대신한다. SQL Server 에서는 클러스터 키 `Id` 가 붙어 `At`·`Id` 커서까지 인덱스로 찾는다). Excel 은 전체 활동(`ViewAsync(id, activityLimit: null)`). 수정 화면은 기본 정보·내역만(`LoadInfoAsync`).
- **협업 조회**(4.1): 새 활동 수는 그룹 쿼리 하나, 새 소식은 EXISTS 조건, 활동 쪽의 멘션은 Id 범위로 읽어 메모리에서 거른다(목록 매개 변수 없이). 알림은 활동과 같은 SaveChanges 로 저장한다(`AppDb` 저장 훅 — 저장 직전 `ChangeTracker.DetectChanges` 로 활동의 과제를 맞춘 뒤 과제 담당·관심자 한 번, 작업 담당 한 번 읽는다). 상세 GET 은 방문 기록 읽기·저장과 관심 여부, 멘션 조회가 더해진다.
- **요청 안에서 기준 정보는 한 번만**: `ProjectService` 가 위치·공휴일을 요청 동안 기억한다(달력 계산과 화면의 공휴일 목록이 같은 행을 쓴다). 요청 사이에는 기억하지 않는다 — 표가 작아 얻는 것이 적고 관리 화면 변경의 무효화를 엮는 비용이 더 크다. 담당자 이름 목록은 이름 열만 읽는다.
- **보내는 양**: 응답 압축(Brotli·Gzip, `CompressionLevel.Fastest`, JSON 포함)을 정적 파일 앞에 둔다. Kestrel 단독 서비스라 앞단에서 압축해 줄 곳이 없다. 운영이 HTTP 라 `EnableForHttps` 는 기본값(꺼짐) — HTTPS 로 바꾸면 비밀 값이 든 응답의 BREACH 위험을 먼저 검토한다. JSON 인코더는 `JavaScriptEncoder.Create(UnicodeRanges.All)`(`AppJson.Encoder`, MVC 응답도 같은 것)이라 한글을 그대로 내보내면서 `<`·`>`·`&`·따옴표는 계속 이스케이프한다(페이지에 심은 JSON 이 `</script>` 로 끊기지 않는다). `UnsafeRelaxedJsonEscaping` 은 쓰지 않는다. null 필드 생략은 화면이 `=== null` 로 비교하는 곳이 있어 하지 않는다. 대시보드 간트는 쓰는 값만 담은 `TimelineView` 를 싣고(과제당 크기가 절반 이하), 간트 영역은 화면 높이 안에서 스크롤한다(`gantt-host tall`, 머리글 고정).
- **회귀 시험**: 시험 프로젝트에만 둔 `DbCommandInterceptor`(`CommandCounter`)로 상세 GET·체크 변경·대시보드의 DB 명령 수에 상한을, 대형 과제(작업 200·활동 3,000) 도우미(`BigProject`)로 상세 JSON 크기·압축률·활동 쪽 경계·변경 이력 쪽 나누기와 필터를 단언한다. 정확한 값이 아니라 상한이다(EF 버전에 따라 분할 쿼리 수가 조금 달라질 수 있다). 가짜 EF(섀도 빌드)의 `Include` 는 아무 일도 하지 않으므로 변경 경로마다 진짜 DB 로 결과를 확인하는 서비스 시험을 둔다(`DataAccessTests`).

## 8. 자동 업데이트

데스크톱 프로그램의 자기 교체 방식(매니페스트 확인 → 받기 → 검증 → 교체 → 되돌리기)을 웹 서버에 맞게 바꿨다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 누가 바뀌나 | 서버 한 곳. 브라우저는 서버가 바뀐 것을 알아채고 새로 고침만 한다 | 사용자 PC 에 깔린 것이 없다 |
| 배포 형태 | win-x64, 런타임 포함 폴더를 zip 하나로 | 서버에 .NET 을 따로 맞출 필요가 없다. 단일 exe 는 wwwroot·설정 파일과 맞지 않아 쓰지 않는다 |
| 실행 방식 | Windows 서비스(Kestrel 단독). IIS 는 대안 | 서비스는 항상 떠 있어 야간 확인·적용이 그대로 돈다(IIS 는 기본 설정에서 20분간 요청이 없으면 앱을 내린다). IIS·Hosting Bundle 을 설치하지 않아도 되고, 등록부터 업데이트 재시작까지 CI 에서 실제로 시험할 수 있다 |
| 서비스 계정 | 전용 계정 `NT SERVICE\<이름>`. 폴더 수정 권한과 자기 서비스 시작·중지 권한만 준다 | 사내망에 열린 웹 서버를 SYSTEM 으로 돌리지 않는다. 권한은 파일 교체, 교체 뒤 재시작, 시작되지 않은 새 버전을 멈추고 되돌리는 데 필요하다(예전 설치는 `install` 을 다시 실행하면 중지 권한이 더해진다. 없어도 도우미가 프로세스를 직접 끝낸다) |
| 설치 | `GanttScheduler.exe install` (`install-service.cmd`) — 실행 파일이 직접 `sc`·`icacls`·`netsh` 를 부른다 | PowerShell 스크립트는 사내 실행 정책에 막힐 수 있다 |
| 버전 확인 | `github.com/<레포>/releases/latest/download/GanttScheduler.json` → `releases/latest` 리다이렉트 → `api.github.com`(짧은 시간 제한). 앞 단계가 "없음(404)"이면 그것을 대표 원인으로 알린다 | 사내망은 api.github.com 이 막혀 있다. 막힌 주소의 시간 초과가 "응답 없음"으로 바뀌어 진짜 원인을 가리지 않게 한다. 주소·폴더로도 바꿀 수 있다(`Update:Source`) |
| 배포 위치 | 소스는 비공개 레포, 배포 파일은 공개 레포 `Gantt_Scheduler_Release` 의 릴리스 | 비공개 레포의 릴리스는 서버가 로그인 없이 읽을 수 없다. 서버에 토큰을 두지 않으려고 배포 파일만 공개한다 |
| 검증 | 매니페스트의 SHA-256 과 대조. `.partial` 로 받고 맞을 때만 풀어 둔다 | 손상·중단 파일 방지 |
| 출처 확인(서명) | 빌드에 공개키(`update-key.pub`, ECDSA P-256)가 들어 있으면 매니페스트 옆의 분리 서명(`GanttScheduler.json.sig`, SHA-256·DER)이 맞아야 받는다. 서명은 정식 배포 워크플로가 시크릿 `RELEASE_SIGNING_KEY` 로 만든다. 폴더·사내 주소 소스와 파일로 올리기도 같은 규칙(올릴 때 zip·매니페스트·서명 세 파일). 공개키가 없는 빌드는 예전처럼 SHA-256 만 보고 화면에 "서명 검증 꺼짐"을 보인다 | SHA-256 은 같은 곳에서 받은 값끼리 비교해 손상만 잡는다. 릴리스 계정·토큰이 털리면 자동 적용이 켜진 모든 서버가 남의 코드를 실행하므로, 개인키를 따로 둔 서명으로 출처를 확인한다. 공개키 파일에 키를 여러 개 둘 수 있어(하나라도 맞으면 받음) 키를 바꿀 수 있다 |
| 시작 확인 | 새 버전은 요청을 받기 시작하면(`ApplicationStarted`) `App_Data/updates/started.json` 을 남긴다. 교체 도우미는 다시 띄운 뒤 정해진 시간(기본 120초, `Update:VerifySeconds`) 안에 새 버전의 표시가 없거나 프로세스가 먼저 끝나면 실패로 본다 | 시작 명령이 받아들여진 것만으로는 새 버전이 떴는지 알 수 없다. 자동 적용은 무인 시간대에 돌아 아침까지 서버가 멈춰 있을 수 있다 |
| 시작 실패 | DB 구조가 같으면 새 버전을 내리고 이전 버전으로 되돌려 다시 띄운다. 상태 파일은 교체 전으로 돌려놓고 그 버전을 `SkipAuto`(되돌린 버전)와 새 항목 `StartFailure`(이유·시작 오류 앞부분)에 기록한다. 업데이트 화면은 이유와 "다시 시도"(받아 둔 파일로 적용 또는 다시 받기)·"안내 닫기"를 보인다. 구조가 다르면 되돌리지 않고 "백업 복원 후 이전 버전 설치"를 결과에 남긴다 | 도우미는 새 버전의 실행 파일이라 옛 서버가 띄워도 이 확인을 한다. 되돌아간 옛 버전이 이 기능을 몰라도 `SkipAuto` 는 알기 때문에 밤마다 같은 버전을 다시 적용하지 않는다. 마이그레이션이 이미 적용됐을 수 있는 경우에는 프로그램만 되돌리면 안 된다 |
| 교체 시점 | 관리자가 누를 때, 또는 설정한 시간대에 한동안 요청이 없을 때 | 서버는 "닫을 때"가 없다. 해외 법인의 근무 시간일 수 있어 시간대만으로 정하지 않는다 |
| 교체 방법 | 받아 둔 새 버전 폴더의 실행 파일을 `--apply-update` 로 따로 띄워 맡긴다 | 실행 중인 서버는 자기 파일을 바꿀 수 없다. 스크립트(PowerShell 등)는 사내 실행 정책에 막힐 수 있다 |
| 교체 범위 | 패키지 목록(`package.files`)에 있는 파일만. `App_Data`, 서버에서 고친 설정, 직접 넣은 파일은 그대로 | 데이터와 서버별 설정을 지키기 위해 |
| DB | 구조가 바뀌는 업데이트(마지막 마이그레이션이 다름)는 자동 적용하지 않고, 프로그램만 되돌리는 것도 막는다 | 마이그레이션은 시작할 때 적용되고 되돌릴 수 없다 |
| 되돌리기 | 직전 버전 한 세대 보관. 되돌린 버전은 자동으로 다시 적용하지 않는다 | 배포 사고 복구 |
| 적용 전 백업 | DB 구조가 바뀌는 업데이트는 적용을 누르면 먼저 DB 백업과 파일 묶음을 만든다(`Backup:BeforeSchemaUpdate`, 기본 켬). 백업은 요청과 떼어 돌리고(단계 `backing-up`, 화면은 상태를 다시 물어 기다린다) 끝나면 교체를 시작한다. 실패하면 적용하지 않고 이유를 보인다. 백업 이름은 교체 기록(`PendingSwap.Backup`)을 거쳐 적용 이력(`UpdateLog.Backup`)에 남고, 되돌리기가 막힌 안내에 "복원할 백업" 으로 보인다 | 구조가 바뀐 버전은 프로그램만 되돌릴 수 없어 백업이 유일한 복구 수단이다. 화면이 "백업하세요" 라고 안내만 하면 백업 여부를 확인하지 않고 적용된다 |
| 채널 | `release`(정식) · `dev`(main 시험) · `local`(로컬 빌드, 교체 안 함) | 개발 중인 폴더를 바꾸지 않도록 |

교체 순서 (`Services/UpdateApplier.cs`):

0. (DB 구조가 바뀌는 업데이트) 서버가 먼저 백업한다(`BackupService`). 실패하면 여기서 멈추고 받아 둔 업데이트는 그대로 둔다.
1. 서버가 도우미를 띄우고 1.5초 뒤 스스로 내려간다(서비스는 "중지됨" 상태가 된다).
2. 도우미가 `app_offline.htm` 을 둔다. IIS 로 운영할 때 앱을 내리고 "업데이트 중" 화면을 보여 주게 하는 파일이고, 서비스 방식에서는 쓰이지 않는다.
3. 서버 프로세스가 끝나고 실행 파일 잠금이 풀리기를 기다린다(최대 3분). 안 풀리면 아무것도 바꾸지 않는다.
4. 지금 파일을 `App_Data/updates/previous` 로 옮기고 새 파일을 복사한다. 도중에 실패하면 옮긴 파일을 되돌린다.
5. 결과를 기록하고 서버를 다시 띄운다 — 서비스는 `sc start`(실패했어도 원래 버전이 다시 떠야 하므로 항상 실행), IIS 는 다음 요청 때 스스로, 직접 실행한 서버는 같은 명령으로.
6. (적용, 서비스·직접 실행) 새 버전이 시작 표시(`started.json`)를 남길 때까지 기다린다. 시간 안에 없거나 먼저 끝나면, DB 구조가 같을 때 새 버전을 내리고(서비스 중지·남은 프로세스 종료) 보관해 둔 이전 버전으로 되돌린 뒤 다시 띄운다. 시작 오류(`App_Data/startup-error.log`)의 앞부분을 결과와 상태에 남긴다. IIS 는 도우미가 띄우지 않으므로 확인하지 않는다.
7. 다시 뜬 서버가 결과를 이력에 남기고 남은 파일을 정리한다. 성공 여부는 지금 버전이 목표 버전인지로 정한다(결과 파일은 실패 이유를 준다). 방금 적용한 받아 둔 폴더(`staged/<버전>`)는 새 버전이 요청을 받기 시작(`ApplicationStarted`)한 뒤의 정리 때 지운다 — 시작 단계를 마치고도 요청을 받기 전에 죽으면 도우미가 상태를 교체 전으로 되돌려 '다시 시도'가 그 폴더를 쓰기 때문이다(도우미 자신도 그 폴더에서 돌며 기다린다). 적용·시작 때는 받아 둔 폴더에 패키지 목록(`package.files`)의 파일이 모두 있는지 보고, 빠졌으면 버리고 다시 받게 한다.

도우미 인자는 추가만 한다. 이번에 더한 `--verify-seconds`·`--from-schema`·`--to-schema` 는 옛 도우미가 무시하고, 새 도우미는 없으면 기본값(120초, 상태 파일의 `Pending.FromSchema`, 자기 빌드의 SchemaId)을 쓴다. 서버는 시작하다 죽으면(서비스·직접 실행 모두) 원인을 `App_Data/startup-error.log` 에 남긴다.

서버가 요청을 받기 전에 하는 일(DB 마이그레이션, 직전 교체 결과 정리)은 호스트 시작 단계(`StartupWork`)에서 돌린다. Windows 서비스는 프로세스가 뜬 뒤 30초 안에 서비스 관리자에 연결해야 하는데 그 연결이 호스트 시작 때 이뤄지므로, 그 전에 DB 작업을 하면 마이그레이션이 길 때 서비스 시작이 실패한다.

### 8.1 백업 (`Services/BackupService.cs`)

| 항목 | 결정 | 이유 |
|---|---|---|
| DB | SQL Server: `BACKUP DATABASE <DB_NAME()> TO DISK=@path WITH COPY_ONLY, CHECKSUM, INIT`, 압축 없음. SQLite: `VACUUM INTO @path` | COPY_ONLY 는 DBA 의 백업 체인(차등·로그)을 깨지 않는다. Express 판은 압축을 지원하지 않는다. VACUUM INTO 는 쓰는 중에도 일관된 사본을 만든다 |
| 경로 | `Backup:Path` 는 **SQL Server 컴퓨터 기준**(절대 경로·UNC, 상대 경로는 거절). 비우면 SQL Server 의 기본 백업 폴더. 이 서버에서 그 파일을 열 수 있는 경우(SQLite, 같은 컴퓨터의 SQL Server, UNC)에만 크기 확인·정리를 한다 | BACKUP 파일은 SQL Server 서비스 계정이 그 컴퓨터에 쓴다. 원격 DB 의 `D:\Backup` 은 이 서버의 같은 이름 폴더와 다른 곳이라 건드리면 안 된다 |
| 파일 묶음 | 첨부(`Storage:Path`), 암호화 키, `appsettings.Production.json`, `backup.json`(이름·시각·버전·구조) 을 같은 이름의 zip 으로 `Backup:FilesPath`(앱 서버, 기본 `App_Data/backups`)에 | DB 만 복원하면 첨부가 404 가 된다. 짝을 맞춰 복원할 수 있게 이름(한국 시각)을 같게 한다. SQL Server 는 이름에 DB 이름을 넣는다(`gantt-<DB>-<시각>`) — 한 SQL Server 를 여러 앱이 각자 DB 로 쓰면 기본 백업 폴더가 같아 같은 초의 `INIT` 가 서로의 `.bak` 을 덮어쓴다 |
| 목록 | `Backup:FilesPath/backups.json`, 임시 파일에 쓰고 바꿔치기. 항목은 추가만 한다. 성공한 백업 `Backup:Keep`(7)개를 남기고 오래된 것은 열 수 있는 파일만 지운다. 실패 기록은 남은 가장 오래된 성공보다 새것만(최대 10) | 서버가 바뀌어도 목록을 읽고, 쓰다 끊겨도 깨지지 않게 |
| 시점 | '지금 백업'(업데이트 화면, 관리자), 구조 변경 업데이트 직전, 야간(`Backup:Nightly`, 기본 꺼짐, `Backup:NightlyAt` 한국 시간 — 하루 한 번, 실패한 회차는 다시 하지 않는다. 그 시각에 서버가 꺼져 있었으면 4시간 안에 켜졌을 때만 따라잡는다) | 사내 DB 는 DBA 가 이미 백업하는 경우가 많아 야간 백업은 기본으로 끈다 |
| 한 번에 하나 | 백업이 돌고 있으면 다른 백업 요청은 거절한다 | 같은 파일·DB 에 겹쳐 쓰지 않게 |
| 요청과 분리 | '지금 백업'은 요청 취소(탭 닫기·다른 화면으로 이동)에 묶지 않고 서버 종료에만 멈춘다. 멈춘 백업도 실패('끝나기 전에 멈췄습니다')로 목록·로그에 남는다 | 큰 DB 는 몇 분 걸린다. 백업을 누르고 다른 화면으로 가서 위험한 작업을 할 때 백업이 조용히 사라지면 안 된다 |

복원·서버 이전 절차는 [OPERATIONS.md](OPERATIONS.md).

### 8.2 운영 점검과 로그

- **점검 한 곳** (`Services/OpsChecks.cs`): 결과는 `CheckResult(이름, ok·warn·fail, 원인, 해결 방법)`. DB 왕복, DB 구조(적용된 마이그레이션 vs 이 빌드의 마이그레이션·SchemaId / SQLite 구조 표시 파일), 디스크 여유(작은 디스크는 비율, 큰 디스크는 남은 양), 폴더 쓰기 권한(App_Data·첨부·키·업데이트·로그·백업), 운영에서 SQLite 사용, PDF 글꼴(`PdfFonts` — 내보내기와 같은 탐색), 업데이트 확인 결과, 서명 검증, 첨부 대조(유실·고아·총량), 공휴일(올해, 10월부터 내년), 마지막 백업, 기준 정보. 서버 상태 화면·`/health/ready`(DB·디스크만)·관리자 칩이 같은 판정을 쓴다.
- **첨부 대조**: 과제 번호 폴더만 본다(사람이 넣은 다른 파일은 건드리지 않는다). 파일을 먼저 쓰고 DB 에 기록하는 올리기 순서 때문에 10분 안의 파일은 고아로 보지 않는다. 고아 정리는 지우기 직전에 다시 대조하고, 과제와 무관한 일이라 활동 이력 대신 로그에 누가·몇 개를 남긴다.
- **파일 로그** (`Services/FileLog.cs`, 공유 프레임워크만 써서 섀도 빌드에서도 컴파일): 한국 날짜별 `Logs:Path/yyyy-MM-dd.log`, 큐에 넣고 백그라운드에서 쓴다(요청을 늦추지 않는다). 날짜가 바뀐 뒤 처음 쓸 때 `Logs:KeepDays`(30)일이 지난 파일을 지운다. 경고 이상 최근 200건은 메모리(링 버퍼)에 둬 서버 상태 화면이 보인다. 호스팅의 요청 범위에서 요청 번호를 꺼내 줄마다 붙인다(오류 번호와 같은 값).
- **느린 요청**: `Logs:SlowRequestMs`(1000)를 넘긴 요청은 경고로 남긴다. 일부러 오래 걸리는 관리 작업(올리기·확인·백업)은 정보 수준. 성능 개선 순서를 가상 데이터가 아니라 운영 기록으로 정하기 위해서다. 모든 응답에 `Server-Timing: total;dur=<ms>`(응답을 보내기 시작할 때까지의 서버 시간)를 붙여, 사용자 PC 의 개발자 도구에서 느린 원인이 서버인지 네트워크인지 바로 가른다.
- **업데이트 진단 정보**: 업데이트 화면(관리자)에서 `apply.log` 끝 60줄, `startup-error.log`, 상태 요약(버전·단계·확인 결과·받아 둔 버전·이전 버전·진행 중 교체·시작 실패·최근 이력)과 최근 업데이트·백업 경고를 보고 텍스트 한 파일로 내려받는다. 상태 파일에 확인 성공 시각(`LastCheckOkAt`)과 실패 시작 시각(`CheckFailedSince`)을 더했다(항목 추가).

브라우저 쪽 (`wwwroot/js/app.js`):

- 모든 화면이 1분마다(보이는 탭만) `/version` 을 묻는다. 서버의 빌드가 화면을 받았을 때와 다르면 "새 버전이 적용되었습니다 · 새로 고침" 띠를 띄운다. 입력 중일 수 있어 자동으로 새로 고치지 않는다.
- 업데이트 중이라고 들은 뒤의 끊김은 안내만 하고, 예고 없는 끊김은 두 번 연속 실패했을 때 경고로 표시한다. 돌아오면 사라진다.
- 저장 요청이 업데이트 도중(503)에 걸리면 "잠시 후 다시 시도" 로 안내하고 입력 창을 닫지 않는다.
- 위조 방지 토큰의 키를 `App_Data/keys` 에 두어, 서버가 바뀐 뒤에도 열려 있던 화면에서 그대로 저장할 수 있다. Windows 서비스로 돌면 키 파일을 DPAPI(이 컴퓨터 범위)로 암호화한다. 이미 평문으로 저장된 키는 그대로 읽히고 새 키부터 암호화된다.
- 사람이 보내지 않은 요청은 "사용 중"으로 세지 않는다(자동 적용의 유휴 판단): `/version`·`/health` 와, 화면이 주기적으로 보내며 `X-Background: 1` 머리글을 붙인 요청(`App.poll` — 상세 화면의 변경 확인, 업데이트 화면의 진행 상태). 세면 상세 화면을 켜 둔 PC 하나 때문에 받아 둔 업데이트가 밤새 적용되지 않는다.

실제로 서버를 내렸다 올리는 흐름은 `tools/release/selftest.sh` 가 확인한다(확인 → 받기 → 적용 → 파일 올리기 → 되돌리기 → 시작하자마자 죽는 버전의 자동 되돌림, 데이터·설정 보존, 시험용 키로 서명 확인). Windows 서비스로 등록한 형태(운영과 같은 형태), Windows·Linux 에서 직접 실행한 형태 세 가지로 돈다.

배포 파이프라인 (`.github/workflows`):

- 정식 배포는 그 커밋의 CI(빌드·SQLite·SQL Server 테스트·화면 점검)가 성공한 경우에만 태그·릴리스를 만든다(실행 중이면 기다린다). 테스트를 다시 돌리지 않는다.
- 정식 배포와 main 의 테스트 빌드는 동시 실행 그룹이 달라, main 에 push 해도 진행 중인 정식 배포가 취소되지 않는다. 테스트 빌드(`dev`)는 CI 가 성공한 뒤에만 만든다.
- 저장소에 공개키가 있는데 서명 시크릿이 없으면 정식 배포는 태그를 만들기 전에 멈춘다. 만든 서명은 저장소의 공개키로 확인하고, 공개 레포에 올린 뒤 서버와 같은 주소로 받아 다시 확인한다.
