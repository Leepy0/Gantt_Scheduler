# 설계

과제 진척 대시보드(TaskBoard)와 간트 스케줄러(GanttScheduler)를 하나로 합쳐 다시 설계한 내용. 두 프로젝트의 코드는 가져오지 않고 개념만 이어받았다.

## 1. 무엇을 합쳤나

| | 이전 TaskBoard | 이전 GanttScheduler | 통합 후 |
|---|---|---|---|
| 보는 범위 | 여러 과제를 넓게 | 과제 하나를 깊게 | 대시보드(넓게) → 과제 상세(깊게) |
| 구조 | 과제 → 단계(목표일/완료일) | 프로젝트 → 단계 → 작업(목표/실적 기간) | **과제 → 단계 → 작업** |
| 사용자 | 접속 IP ↔ 이름 | 자유 입력 담당자 | 사용자 한 종류(IP 는 여러 개 연결 가능, IP 없는 담당자도 허용) |
| 이력 | 변경 로그 | 댓글 + 계획 변경 로그 | 활동(댓글·변경) 한 스트림 |
| 위치 | 법인/제품군/라인/층 4개 테이블 | 없음 | 단일 트리 테이블(Location) |

핵심은 **단계는 약속 일정(마일스톤), 작업은 그 안의 세부 일정**이라는 구분이다. 소형 과제는 단계 날짜만으로 관리하고, 대형 과제만 단계 아래에 작업을 붙인다.

## 2. 확정한 규칙

1. **단계 목표일은 사람이 정한다.** 작업 일정에서 자동으로 덮어쓰지 않는다. 대신 작업들의 가장 늦은 종료일을 "작업 기준 예상 종료"로 따로 보여 주고, 목표일을 넘으면 경고한다.
   - **목표일 초안은 제안일 뿐이다.** 과제 등록 화면은 유형·착수일을 고르면 단계 템플릿의 기본 기간(`StageTemplate.DefaultWorkDays`, 근무일)으로 초안을 계산해 표로 보여 준다(`Rules.DraftTargets`). 앞 단계 목표일(첫 단계는 착수일)에서 근무일 기본 기간만큼 뒤이고, 기본 기간이 없는 단계는 비우며 그다음 단계는 앞에서 정해진 마지막 목표일부터 센다. 사람이 고친 줄(빈 값 포함)은 그대로 두고 그 뒤 단계만 거기서 다시 센다. 사람이 확인하고 등록해야 목표일이 되며, 서버가 저절로 채우지 않는다. 기본 기간은 과제에 복사하지 않는다(나중에 바꿔도 기존 과제에 영향 없음).
   - **같은 거리 하나**: 기본 기간·초안·단계 일정 표의 근무일 간격(`Rules.TargetGaps`, `StageView.GapWorkDays`)·관리 화면의 과거 평균 힌트가 모두 "앞 단계 목표일(첫 단계는 착수일)부터 이 단계 목표일까지의 근무일 거리(`WorkCalendar.Distance`)"를 쓴다. 초안을 그대로 두면 간격 = 기본 기간이고, 과거 평균을 기본 기간에 그대로 옮겨 쓸 수 있다.
   - **과거 평균 힌트**(`Reporting.StageLeadHints`): 같은 유형·같은 이름 단계가 완료된 과제(모든 단계 완료)에서 걸린 근무일(앞 단계 완료일부터)의 평균. 표본(과제)이 3건 이상일 때만 보인다(`LeadHintMinSamples`). 앞 단계와 같은 날 또는 먼저 완료한 기록(0 이하)은 몰아서 완료 처리한 것으로 보고 빼고, 기준점은 지금까지 가장 늦은 완료일로 둔다(순서를 거슬러 완료한 단계 뒤가 길게 잡히지 않게).
2. **진행률**: 단계 = 완료면 100, 작업이 있으면 작업 진행률 평균, 없으면 0. 과제 = 단계 진행률의 평균.
3. **상태는 저장하지 않고 계산한다** (단계·작업). 날짜와 상태가 어긋나는 일이 없다.
   - 단계: 완료일 있음 → 완료 / 목표일 지남 → 지연 / 순서상 첫 미완료 → 진행 중 / 나머지 → 예정
   - 작업: 실적 종료 있음 → 완료 / 실적 시작 있음 → 진행 중 / 없음 → 예정. 목표 종료가 지난 미완료는 지연, 목표보다 늦게 끝난 완료는 "초과 완료"
   - **완료된 단계의 작업은 단계와 함께 끝난 것으로 본다.** 실적 종료가 비어 있어도 지연·임계·내 할 일·다음 주 계획에서 빼고, 의존 관계로 밀지도 않는다(`Rules.IsOpen`·`IsMovable`). 화면은 이런 작업을 "완료(단계)"로 표시하고 실적 막대를 단계 완료일에서 끊으며, 간트에서 끌어 옮기지 않는다(`Rules.IsClosedByStage` → `ClosedOn`). 단계를 완료할 때 "남은 작업 n건을 완료일로 닫고 완료"를 고르면 작업마다 실적(시작이 없으면 목표 시작일, 종료는 완료일)과 진행률 100% 를 넣고 이력을 남긴다. 완료를 취소하면 그 단계의 미착수 작업을 그 사이 늦어진 선행에 맞춰 규칙 11 의 밀기로 다시 맞춘다(같은 BatchId 로 작업당 이력 1건).
4. **과제 상태**는 진행/보류/중단/완료. 완료는 모든 단계가 끝나면 자동으로 바뀌고, 완료 취소 시 다시 진행으로 돌아온다. 보류·중단은 사유 필수.
5. **목표일을 바꿀 때는 사유 필수** (단계 목표일, 작업 목표 일정). 처음 정할 때는 사유 없이 기록만 남긴다.
   - 등록할 때 정한 목표일도 처음 정하는 것이라 "목표일 설정"(사유 없음)으로 남긴다. 단계 Id 는 저장 뒤에 정해지므로 이 기록은 단계명으로만 남긴다(단계 추가 기록과 같다).
   - **단계 일정 표**(상세 "단계 일정 편집", `ProjectService.SaveStageScheduleAsync`): 여러 단계의 목표일·완료일을 한 번에 저장한다. 화면은 바꾼 단계만 보내고, 서버는 단계마다 화면이 본 버전을 확인한다(바꾸지 않은 단계는 다른 사람이 동시에 고쳐도 충돌이 아니다). 이미 정한 목표일을 바꾸거나 지우는 단계가 하나라도 있으면 사유를 한 번 받아 그 단계들의 기록에 모두 남기고, 모든 기록(목표일·완료·작업 밀기)을 BatchId 하나로 묶는다. 완료는 단계 시트와 같은 내부 메서드(`EnsureCanComplete`·`SetCompleted`·`RealignReopenedAsync`)를 거친다 — 체크리스트가 남으면 거절, 완료 취소 시 그 단계 작업을 선행에 맞춰 밀기(여러 단계를 다시 열어도 한 번에 계산해 작업당 1건), 과제 자동 완료·재개. 표에서 완료하면 남은 작업은 "완료(단계)"로 본다(작업마다 실적을 넣으려면 단계 시트의 "남은 작업을 완료일로 닫고 완료"). 검사를 모두 통과한 뒤에만 값을 바꾸므로 한 줄이라도 거절되면 아무것도 바뀌지 않는다. 연쇄 이동은 표에서 모든 단계를 직접 고치므로 두지 않는다.
   - 표의 간격·추천 입고일은 고치는 동안 미리보기 요청(`SchedulePreviewAsync`, 저장하지 않음)으로 서버가 다시 계산한다(화면이 근무일을 세지 않는다). 동시 수정으로 거절되면 규칙 14 의 세 갈래 비교로 표를 최신 단계로 다시 그린다(삭제·추가된 단계 포함).
6. **연쇄 이동**: 단계 목표일을 바꿀 때 이후 미완료 단계를 같은 **근무일 수**만큼 함께 옮길 수 있다. 한 번의 사유로 묶어 기록한다(BatchId).
   - "이후 단계의 미착수 작업 n건도 같은 근무일 수만큼 이동"을 고르면(기본 꺼짐) 그 작업들도 근무일 기간을 지킨 채 옮긴다. 당겨서 앞 단계 선행과 어긋나는 작업은 규칙 11 의 밀기로 다시 맞춘다. 작업마다 처음 → 마지막 일정으로 이력 1건(같은 BatchId·사유).
7. **입고 추천일** = 검수 단계 일자(완료일 우선, 없으면 목표일) + 법인의 해상 운송 소요일. 입고 단계 편집 시 추천값으로 보여 준다. 단계 일정 표와 등록 초안도 같은 규칙(`Rules.InboundRecommendation`)으로 저장 전 날짜에서 계산해 "적용" 단추로 보여 준다. 초안은 추천일을 저절로 넣지 않는다(샘플 기준 정보의 입고는 법인마다 운송 기간이 달라 기본 기간을 비워 둔다).
8. **지연 판정의 '오늘'은 한국 시간** 기준. 법인별 시간대는 두지 않는다.
   - 화면은 페이지를 받을 때의 날짜를 계속 쓰지 않는다. 변경 응답·`/version`(1분마다·탭이 다시 보일 때)이 한국 날짜(`today`)를 싣고, 날짜가 바뀌었으면 상세 화면은 최신 과제를 다시 읽어 그린다(자정을 넘겨 열어 둔 화면이 어제 날짜로 저장하거나 지연 표시가 어긋나지 않게).
   - **실적 날짜의 기본값은 접속한 PC 의 날짜**다: '오늘 시작·오늘 완료' 단추, 미래 날짜 경고, 진행률만 올린 작업에 넣는 실적 시작. 해외 법인(한국보다 늦은 시간대)에서 저녁에 누르면 한국은 이미 다음 날이라 하루 뒤 날짜가 기록되기 때문이다. 화면이 PC 날짜(`clientToday`)를 보내고, 서버는 한국 날짜 ±1일(`Rules.ClientDayWindow`) 안이면 그 값을, 아니면(PC 시계가 틀림) 한국 날짜를 쓴다(`Rules.UserToday`). 단추가 넣는 날짜는 사용자가 고칠 수 있는 입력값이라 서버가 바꾸지 않으므로, 화면(`App.userToday`)이 같은 허용 범위를 서버에게서 받아(`data-day-window`) 지킨다.
9. 기준 정보는 지우지 않고 **사용 중지**한다(기존 과제에 계속 표시). 단계 템플릿과 공휴일만 바로 삭제한다. 단계 템플릿은 과제 생성 시점에 복사되므로 나중에 바꿔도 기존 과제는 영향이 없다.

10. **근무일**: 주말과 관리 화면의 공휴일을 뺀 날. 기간 표시(근무일 n일), 연쇄 이동, 의존 관계에 따른 일정 밀기, 여유, 복제에 쓴다. 지연 일수(D+n)는 달력 날짜 기준 그대로다.
    - 계산은 "그날까지의 누적 근무일 수"를 주 단위 산술과 정렬된 공휴일 목록의 이분 탐색으로 구해 그 차이로 한다(`WorkCalendar`). 기간이 길어도 하루씩 돌지 않고, 날짜 끝에서 넘치지 않는다.
11. **의존 관계**는 "선행이 끝나야 후행을 시작"(FS) 한 가지다. 후행은 선행 종료 다음 근무일(+간격) 이후에 시작해야 한다. 판정은 모두 `Rules.EarliestStart` 하나를 거친다(다른 유형을 더할 자리).
    - 순환 연결은 거절한다. 사람이 입력한 일정이 선행보다 이르면 거절하는데, **밀기 대상(미착수·단계 미완료) 작업이 새로 생기거나, 그 작업의 목표 일정·선행 집합을 바꾸거나, 실적 시작을 지우거나 열린 단계로 옮겨 밀기 대상이 될 때만** 검사한다. 제목·담당·메모·진행률만 고칠 때는 이미 남아 있던 위반(공휴일 추가 등으로 생긴)이 있어도 저장되고, 위반은 화면에 표시된다. 밀기·위반 표시·이 검사는 모두 같은 판정(`Rules.IsMovable`)을 쓴다 — 이미 시작했거나 완료된 단계의 작업은 밀지도, 위반으로 표시하지도, 날짜를 검사하지도 않는다.
    - 선행 일정이 늦어지면 **아직 시작하지 않은** 후행은 근무일 기간을 유지한 채 자동으로 밀린다(`Rules.Reschedule`). 바뀐 작업에서 닿는 후행만 위상 정렬 순서로 보고, 선행이 여럿이면 모든 선행이 정해진 뒤 가장 늦은 요구에 맞춰 **한 번만** 옮긴다. 이력은 작업당 1건(같은 BatchId). 이미 시작한 후행과 완료된 단계의 작업은 건드리지 않고, 앞으로 당기지는 않는다.
    - **여유** = 일정을 미뤄도 단계 목표일과 후행 작업에 영향이 없는 **근무일 수**. 목표일이 주말이고 작업이 직전 금요일에 끝나면 여유 0 이다. 미완료이고 여유가 0 이하인 작업이 **임계 작업**이다.
12. **기준선**은 "기준선 확정"을 누른 시점의 단계 목표일·작업 목표 일정을 따로 저장한 것이다. 이후 일정이 바뀌면 기준선 대비 +n일로 보여 준다. 다시 확정하면 덮어쓴다.
13. **체크리스트**: 단계에 체크 항목을 둘 수 있고, 남은 항목이 있으면 단계를 완료할 수 없다. 유형의 단계 템플릿에 기본 항목을 넣어 두면 과제 생성 시 복사된다.
14. **동시 수정**: 과제·단계·작업에 버전 번호를 둔다. 화면이 읽은 버전과 저장 시점의 버전이 다르면 저장을 거절하고(HTTP 409) 화면을 최신 내용으로 바꾼다. 뒤에 저장한 사람이 앞사람 내용을 모르고 덮어쓰는 일을 막는다.
    - 거절된 편집 창(상세 시트·끌기 사유 창·과제 수정 화면)은 닫지 않고 최신 버전으로 바꿔 **같은 창에서 다시 저장**할 수 있게 한다. 칸마다 세 갈래(연 때의 값·최신 값·지금 입력)로 비교해, 내가 손대지 않은 칸은 최신 값으로 바꿔 넣고("다른 사용자가 바꾼 값: … — 그 값으로 바꿨습니다"), 둘 다 바꾼 칸은 내 입력을 두고 상대 값을 옆에 보인다. 손대지 않은 칸을 옛 값 그대로 다시 저장하면 앞사람의 변경을 되돌리기 때문이다. 과제 수정 화면은 연 때의 값을 숨은 입력(`Form.Base`)으로 들고 다닌다(표시용, 저장에는 쓰지 않는다). 읽기와 저장 사이에 끼어든 변경(`DbUpdateConcurrencyException`)도 같은 방법으로 처리한다.
15. **과제 복제**: 단계·체크 항목·기기/용기 내역을 복사하고, 날짜는 원본 착수일로부터의 **근무일 거리** 그대로 새 착수일에 맞춰 옮긴다(작업은 근무일 기간 유지). 달력 일수로 옮기면 요일이 바뀌어 주말에 놓이거나 기간이 줄고 의존 위반이 생기기 때문이다. 남은 위반은 규칙 11 의 밀기로 정리한다. 작업과 의존 관계는 선택. 실적·진행률·완료·활동·첨부·기준선은 복사하지 않는다.
16. **날짜 범위**: 단계 목표·완료일, 작업 목표·실적 일자는 2000-01-01 ~ 2099-12-31 이면서 과제 착수일 1년 전 ~ 10년 뒤 안이어야 한다. 착수일(등록·수정·복제)은 오늘 기준 앞뒤 10년. 연도 오타 하나가 근무일 계산이나 간트 그리기를 멈추게 하지 않도록 서버에서 거절한다(`Rules.ValidateDate`). 바뀐 날짜만 검사하므로 이전에 들어간 값이 있어도 다른 수정은 막지 않고, 착수일을 옮겨 기존 일정이 범위 밖이 되면 거절한다.

규칙 구현은 `Domain/Rules.cs`(계산), `Domain/WorkCalendar.cs`(근무일), `Services/ProjectService.cs`(변경 검증)에 있다.

- 과제의 `CorporationId` 는 `LocationId` 의 최상위(법인)를 미리 풀어 둔 값이다. 법인별 집계를 간단히 하기 위해서다.
- `Activity.StageId / WorkItemId` 는 FK 가 아닌 느슨한 참조다. 단계·작업을 지워도 이력은 남는다.
- 협력사는 과제에 문자열로 저장한다. 관리 화면의 협력사 목록은 자동완성 후보로만 쓴다(목록에 없는 이름도 입력 가능).
- `Version` 은 EF 의 동시성 토큰이다. 저장할 때 서비스가 1씩 올리고, UPDATE 의 WHERE 에도 들어가 읽기~저장 사이에 끼어든 변경을 DB 수준에서도 잡는다.
- 첨부 파일 본문은 DB 가 아니라 디스크(`Storage:Path/과제번호/임의이름`)에 둔다. 원래 파일 이름은 DB 에만 있어 경로 조작 위험이 없다. 허용 확장자만 받는다.
- 사용자의 소속은 조직(OrgUnit) 참조다. 파트에 속하면 "그룹 · 파트"로, 그룹 직속이면 그룹 이름만 표시한다.
- 시각은 UTC 로 저장하고 화면에서 현지 시각으로 바꾼다. 날짜는 `DateOnly`.

화면 구성 원칙:

- 상세 화면은 서버가 준 JSON 하나로 그리고, 변경할 때마다 서버가 최신 과제 전체를 돌려줘 다시 그린다. 클라이언트에 계산 규칙을 두지 않는다. 활동만은 최근 50건(`ProjectService.ActivityPageSize`)과 전체 건수(`activityTotal`)를 싣고, 나머지는 `?handler=Activities&id=&beforeId=`(최근 순, `At`·`Id` 커서)로 나눠 받는다. 화면은 받아 둔 활동과 변경 응답의 최근 활동을 합쳐 그리므로 '더 보기'로 펼친 목록이 저장 뒤에도 남는다. 작업 시트의 진행 내용은 `&workId=` 로 그 작업의 활동만 받는다. 활동 필터·새 소식 같은 기능도 이 조회에 조건을 더해 만든다.
- 간트는 `wwwroot/js/gantt.js` 하나를 대시보드와 상세가 같이 쓴다. 외부 라이브러리·CDN 없음(사내망).
- 간트 끌기는 마우스·펜에서만 동작한다. 터치에서는 화면 스크롤과 겹치므로 막대를 눌러 시트에서 날짜를 고친다. 끌어서 목표 일정을 바꿔도 사유 입력은 똑같이 거친다.
- 모바일: 하단 탭, 과제 상세는 목록 보기가 기본(간트로 전환 가능), 편집 창은 아래에서 올라오는 시트. 입력 요소 48px.
- 색: 평소에는 중립색 + 강조색(#1428A0)만 쓰고, 빨강은 지연, 노랑은 임박·초과 완료에만 쓴다. 상태는 색과 함께 아이콘·글자로 표시한다.
- **표시 규칙은 서버 한 곳**: 임박은 목표일까지 `Rules.SoonDays`(7)일 이하, 단계 초과 완료(`StageView.DoneLate`), 작업의 기준선 대비·지연 일수(`WorkView.SlipDays`·`LateDays`)를 서버가 채운다. 상태 칩(색·아이콘·글자)은 `Views.ProjectChip·StageChip·WorkChip·DueChip` 이 정하고, Razor 는 `_StatusChip` 부분 뷰, JS 는 `App.chip` 이 같은 마크업으로 그린다. Excel·PDF 의 상태 글자도 같은 칩 글자를 쓴다(`ProjectView.StateLabel`). JS 의 휴일 판정은 간트 음영과 입력 안내에만 쓴다.
- **편집 창(시트)**: 입력을 바꾼 뒤 바깥·Esc·닫기·취소로 닫으려 하면 "작성 중인 내용을 버릴까요?"로 묻는다. 바깥 클릭은 누른 곳과 뗀 곳이 모두 바깥일 때만 닫는다(입력칸에서 글자를 끌어 선택하다 바깥에서 떼면 닫히던 문제). 긴 입력(진행 내용·사유·메모)은 그 탭의 sessionStorage 에 임시 저장해, 창을 닫거나 새로 고친 뒤 다시 열면 복원을 제안한다(저장하면 지운다). 첫 포커스는 데스크톱만 첫 입력칸에 준다(모바일은 가상 키보드가 내용을 가리므로 시트 자체).
- **다른 사용자의 변경 알림**: 상세 화면은 1분 확인(`/version`)에 이 과제의 마지막 변경 시각(`?handler=Stamp`, `Project.UpdatedAt` 하나만 읽음)을 함께 묻는다. 화면이 가진 것보다 새것이면 "다른 사용자가 이 과제를 바꿨습니다 · 새로 고침" 띠, 과제가 없으면 "삭제됨" 띠를 띄운다. 입력 중일 수 있어 저절로 새로 고치지 않고, 내 저장은 응답의 최신 과제로 시각을 맞추므로 띠가 뜨지 않는다. 그래서 과제를 바꾸는 모든 경로(댓글·체크리스트·첨부 포함)는 `UpdatedAt` 을 갱신한다.
- **시각**: 화면의 시각은 모두 브라우저 현지 시각으로 같은 형식('MM-dd HH:mm', 올해가 아니면 연도를 붙임, `App.time`)이다. 서버가 그리는 시각은 `<time datetime="…Z">` 로 내보내고 스크립트가 바꾼다. 서버가 만드는 시각·날짜(대시보드 기준 시각, Excel·PDF)는 한국 시간이라고 적는다 — 지연 판정이 한국 날짜 기준이기 때문이다.
- **주소**: 상세의 탭은 주소 해시(`#info`·`#files`·`#activity`)로 남아 새로 고치거나 주소를 보내도 같은 탭이 열린다. 작업 바로가기(`#w123`)는 편집 창을 연 뒤 주소에서 지운다(새로 고침에 창이 다시 뜨지 않게). 목록에서 들어온 상세의 뒤로 단추는 브라우저 뒤로 가기라 목록의 필터·검색이 남는다. 본문 없는 오류 응답(없는 과제 404 등)은 오류 화면으로 다시 그리되, 화면이 JSON 으로 묻는 요청은 JSON 그대로 둔다.
- **인쇄**: 메뉴·도구 모음·탭·알림을 숨기고 A4 가로에 맞춘다. 상세·대시보드는 인쇄 직전 간트를 월 배율로 종이 한 폭에 다시 그리고 끝나면 되돌린다(`App.onPrint`). 의존선은 간트 전체에 걸친 그림 한 장이라 쪽을 나눌 수 없어 인쇄에서 뺀다(위반·임계는 이름 칸 아이콘으로 남는다). 상세·대시보드·내 할 일에 인쇄 단추가 있다(상세는 데스크톱만).
- **오류 번호**: 예기치 않은 서버 오류는 요청 번호(`HttpContext.TraceIdentifier`)를 '오류 번호'로 보인다 — 오류 화면, 화면이 JSON 으로 물은 요청의 500(`{ok:false, error, errorId}`, `JsonErrorMiddleware`), 그리고 5xx 응답의 `X-Error-Id` 머리글(본문이 JSON 이 아니어도 `app.js` 가 안내에 붙인다). 같은 번호가 파일 로그의 `(요청 <번호> <주소>)` 에 남아 관리자가 원인을 찾는다. 내부 예외 메시지는 화면에 보이지 않는다.
- **관리자 알림 칩**: 상단의 칩은 새 버전뿐 아니라 서버 문제를 알린다(`OpsAlerts`, 중요한 것 하나와 나머지 수): 첫 설정 필요(법인이 없어 과제를 등록할 수 없음 — 서버 상태의 첫 설정 점검표로 보낸다), 업데이트 시작 실패·직전 교체 실패(7일 — 시작 실패 안내를 닫으면 그 전의 실패 이력은 다시 알리지 않는다), 자동 확인이 켜져 있고 최근 확인까지 3일 넘게 계속 실패(자동 확인을 끄면 새로 센다 — 끈 서버에 지난 실패 한 번이 영영 남지 않게), 디스크 부족(데이터·첨부·백업 묶음 드라이브 중 하나라도 — 서버 상태·`/health/ready` 와 같은 판정), 백업 실패(2일)·야간 백업을 켰는데 2일 넘게 백업 없음, 10월부터 내년 공휴일 없음. DB·디스크를 읽는 항목은 5분 동안 기억해 화면마다 읽지 않는다(관리 화면에서 법인·공휴일을 고치거나 서버 상태를 열면 바로 다시 읽는다). 일반 사용자에게는 보이지 않는다.
- 접근성: 상세 간트의 이름 칸은 단추라 키보드로 편집 창을 연다. 저장할 때마다 다시 그리는 요약에는 aria-live 를 두지 않고 결과는 토스트(#toasts)가 읽어 준다. 하단 탭은 지금 화면에 aria-current 를 단다.

## 5. 사용자 식별과 권한

로그인이 없다. 접속 IP 로 사용자를 찾고, 처음 보는 IP 는 이름을 등록하게 한다. 같은 이름으로 다시 등록하면 그 IP 가 기존 사용자에 추가로 연결된다(PC 교체·IP 변경 대응). 사내망에서 서로 신뢰한다는 전제이며 다른 사람 이름을 입력하는 것을 막지 않는다. 쿠키 식별·열람자 역할은 두지 않는다.

이 전제는 앱 데이터(과제·일정) 범위의 것이다. 관리자는 업데이트 파일을 올려 서버에서 실행할 수 있으므로, **이름 입력만으로 관리자 권한을 얻는 길**은 막는다.

- **관리자 예외**: 이름 등록·사용자 바꾸기에서 관리자 이름은 이미 그 관리자에 연결된 IP 에서만 받는다. 새 PC 를 쓰게 된 관리자는 다른 관리자가 관리 > 사용자에서 IP 를 추가하거나, 서버 콘솔에서 `GanttScheduler.exe admin <이름> [--ip <주소>]` 로 연결한다(관리자가 혼자이거나 아무도 없을 때의 복구 경로. 웹 서버와 같은 설정으로 DB 를 열고, 마이그레이션은 하지 않으며 구조가 맞지 않으면 안내하고 끝낸다).
- **첫 관리자**: 관리자가 한 명도 없으면 서버 자신(루프백)에서 등록한 사람이 관리자가 된다(`Access:FirstAdminLocalOnly`, 기본 켬). 설치 직후 사내망의 아무 PC 가 먼저 등록해 관리자를 선점하지 못하게 한다. 다른 PC 에서 등록하면 일반 사용자가 되고, 관리 화면에 "서버에서 접속하거나 admin 명령을 쓰라"는 안내가 뜬다.
- **사용자 바꾸기**: 헤더의 내 이름을 누르면 이 기기를 다른 이름으로 다시 연결한다(공용 PC, IP 를 넘겨받은 경우). 이미 아는 IP 의 등록 요청은 이 화면에서 온 것(`switch` 표시)만 받는다. 같은 이름을 입력하면 그 사람에 연결된다는 점(동명이인·오타)을 화면에 적는다. 관리자에 연결된 기기를 다른 이름으로 옮기면 관리자 예외 때문에 그 관리자는 이 기기에서 돌아올 수 없으므로, 되돌리는 방법(다른 관리자의 IP 연결, 관리자가 혼자면 admin 명령)을 보여 주고 확인란을 고른 경우에만 옮긴다. 막지는 않는다 — IP 를 넘겨받은 사람은 자기 이름으로 바꿀 수 있어야 한다.
- **IP 재확인**: IP 연결을 `Access:ReconfirmDays`(기본 30)일 넘게 쓰지 않았으면 "OOO 님이 맞습니까?"를 묻는다. 맞다고 하면 그대로 쓰고, 아니면 사용자 바꾸기로 간다. DHCP 로 IP 가 다른 사람에게 넘어갔을 때 조용히 이전 사람으로 기록되지 않게 하기 위해서다. 마지막 접속 시각은 하루에 한 번만 갱신한다. **관리자 계정은 "맞습니다"로 되살리지 않는다**(서버 자신 제외) — IP 를 넘겨받은 사람이 클릭 한 번에 관리자 권한을 얻게 되기 때문이다. 본인이면 다른 관리자가 관리 > 사용자에서 그 IP 를 다시 연결하거나(이미 연결된 IP 를 다시 연결하면 마지막 접속이 갱신된다) admin 명령을 쓴다. 30일 안에 IP 가 넘어간 경우는 이 확인으로도 막지 못한다(로그인 없는 설계의 남은 위험).
- **접속 허용 대역**: `Access:AllowedNetworks`(CIDR 목록)를 두면 그 밖에서 온 요청은 이름 등록 화면도 없이 403 으로 거절한다. 비어 있으면 모두 받고, 서버 자신(루프백)은 항상 받는다. 방화벽 규칙도 설치 명령의 `--remoteip` 로 같은 대역만 열 수 있다(방화벽의 `LocalSubnet` 은 앱 설정에 쓸 수 없어 실제 대역을 적는다).
- **IP 형식**: 관리 화면의 IP 연결, admin 명령의 `--ip`, 허용 대역, `--remoteip` 는 IPv4 를 앞자리 0 없는 십진수 네 마디로만 받는다. `IPAddress.TryParse` 는 `10` 을 0.0.0.10 으로, 앞자리 0 을 8진수(`192.168.001.010` → 192.168.1.8)로 읽어 엉뚱한 PC 를 관리자에 연결하거나 엉뚱한 대역을 열 수 있기 때문이다(`AccessOptions.TryParseIp`).
- **IP 관리**: 관리 > 사용자에서 사용자별 접속 IP 와 마지막 접속일을 보고, IP 를 직접 연결·해제한다. 지금 쓰고 있는 기기의 IP 는 해제할 수 없다(스스로 잠기지 않게).
- **담당자 이름**: 목록에 없는 이름은 IP 없는 담당자로 만든다(나중에 그 이름으로 등록하면 연결). 저장에 실패하면(동시 수정·사유 누락 등) 만들지 않는다 — 새 사용자를 요청의 마지막 저장에서 함께 저장한다. 사용 중지된 이름은 새로 지정할 수 없다(이미 지정된 것은 그대로 둘 수 있다). 화면은 목록에 없는 이름을 입력하면 "새 담당자로 등록됩니다"라고 알린다.
- 기준 정보 변경은 관리자만, 과제 삭제는 담당자·등록자·관리자만, 첨부 삭제는 올린 사람·과제 담당자·관리자만. 그 외 편집은 등록한 사용자 누구나. 삭제 단추는 지울 수 있는 사람에게만 보인다 — 서버가 같은 판정(`Rules.CanDeleteProject`·`CanDeleteAttachment`)으로 `ProjectView.CanDelete`·`AttachmentView.CanDelete` 를 채운다.
- 리버스 프록시 뒤에 둘 때는 `TrustForwardedHeaders: true` 로 실제 접속 IP(X-Forwarded-For)를 쓴다. 이 값은 같은 서버(루프백)의 프록시가 보낸 것만 믿는다. 같은 서버의 프록시를 이 설정 없이 쓰면 모든 요청이 루프백으로 보여 식별·허용 대역·첫 관리자 규칙이 모두 무력해진다.
- 모든 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: same-origin` 을 붙인다. 첨부 미리보기는 같은 출처의 틀(iframe)이라 그대로 된다.
- 사용자 조회(UserGate)는 `/version`·`/health…`·정적 파일 뒤에 둔다. 열린 화면이 1분마다 묻는 `/version` 에 DB 를 읽지 않고, DB 가 멈춰도 상태 확인은 답하게 하기 위해서다. 감시 도구용 `/health/ready` 는 DB 왕복과 디스크 여유를 보고 실패하면 503 을 준다. 누구나 부를 수 있어 항목 이름과 수준만 주고 원인 문구는 서버 상태 화면(관리자)에만 보인다.
- 서버 상태 화면과 진단 정보·로그 내려받기는 관리자 전용이다(경로·DB 서버 이름이 보인다). 연결 문자열은 서버·DB 이름만 보이고, 진단·로그 파일의 `Password=`·`User Id=` 값은 가린다(`Redact`). 백업 설정·목록도 관리자에게만 내려준다.

## 6. DB

| | 용도 | 스키마 관리 |
|---|---|---|
| SQL Server | 운영 | EF 마이그레이션 — 앱 시작 시 자동 적용. 테이블은 `pm` 스키마. 일시적인 연결 끊김은 EF 재시도 전략(`EnableRetryOnFailure`)으로 다시 시도한다 |
| SQLite | 미리보기·개발·테스트 | 파일이 없으면 그때 새로 만든다(`EnsureCreated`). 모델이 바뀌면(스키마 해시 비교) 새로 만든다 — 개발 환경은 지우고, 그 밖에서는 지우지 않고 `gantt.db.<시각>.bak` 으로 옮겨 둔다 |

마이그레이션은 SQL Server 기준 한 벌만 관리한다. SQLite DB 는 버려도 되는 데이터만 담는다는 전제다. 그래도 운영 설정으로 SQLite 를 쓰는 서버가 있을 수 있어, 개발 환경이 아니면 구조가 바뀌어도 기존 파일을 남긴다(옮기지 못하면 지우지 않고 시작을 멈춘다).

스키마 해시는 EF 가 만든 생성 스크립트의 해시라 EF 패치 버전만 바뀌어도 달라질 수 있다. 패키지 버전은 `Directory.Packages.props` 에 정확한 값으로 고정하고(`packages.lock.json`, CI 는 잠금 모드 복원), 올리는 일은 Dependabot PR 로만 한다.

코드에서 트랜잭션을 직접 열지 않는다(`SaveChanges` 한 번이 트랜잭션 하나). 재시도 전략과 함께 직접 트랜잭션을 쓰려면 `Database.CreateExecutionStrategy()` 안에서 열어야 한다.

조회는 과제 전체를 단계·작업까지 읽어 메모리에서 집계한다. 과제 수백 건 규모에서는 충분하고, 두 DB 의 쿼리 번역 차이를 피할 수 있다. 과제가 수천 건을 넘으면 대시보드·목록 쿼리를 DB 집계로 바꿔야 한다. 그 안에서 요청당 낭비는 줄인다:

- **DB 로 옮기는 조건은 두 DB 에서 똑같이 번역되는 단순한 것만**: 상태·유형·법인 같음, 기간 안 활동 존재(`Any`), 사용자 Id, 활동 유형 같음(`Reporting.KindIs` — 종류를 `KindOf` 로 유형 전부에 대해 역매핑해 `유형 = A OR 유형 = B …` 식을 만든다. 목록 매개 변수(`IN`·`OPENJSON`)는 SQL Server 호환 수준에 따라 번역이 달라 쓰지 않는다). 판정 규칙(지연·임박 등)과 글자 검색(SQLite 는 대소문자 구분, SQL Server 는 정렬 규칙 — 결과가 다르다)은 필요한 열만 읽은 뒤 메모리에서 한다. 그룹 집계·요약 컬럼 저장은 하지 않는다(계산 값을 저장하지 않는 원칙, 2장 3).
  - 목록: 상태 탭·유형·법인은 DB 에서(지연 탭은 진행 과제만 읽고 지연은 메모리에서). 내 할 일: 진행 과제만. 리드타임: 작업 없이 단계만, 중단 과제 제외. 주간 보고: 진행 과제 + 그 주에 활동이 있는 과제(보고에 오르는 과제가 그것뿐이다).
  - 변경 이력: 기간·과제·사용자·종류 조건과 건수·정렬(`At`, `Id` 내림차순)·쪽 나누기를 DB 에서, 열은 과제명만 투영한다. 글자 검색이 있으면 조건에 맞는 행을 투영해 메모리에서 거르고 나눈다. 사용자가 크기를 정하는 조회라 여러 과제의 기간은 1년(`InsightService.HistoryMaxYears`)까지로 맞추고 안내한다. 과제 하나(`projectId`)는 행 수가 그 과제의 활동으로 묶이므로 상한이 없고, 기간을 비우면 그 과제의 첫 활동부터 본다.
- **변경은 필요한 그래프만 추적해 읽는다**(`ProjectService.LoadForChangeAsync`): 단계 → 작업·체크리스트, 의존 관계. 과제 정보 수정·복제만 유형·기기·용기 내역을 더 읽는다. 활동은 읽지 않은 컬렉션에 더해도 저장할 때 INSERT 된다. 댓글은 과제 행만 읽는다. 과제 삭제는 과제 행과 의존 관계만 읽어 의존 관계를 먼저 지우고(같은 SaveChanges 안에서 과제 행보다 앞서 — SQL Server 는 한 문장 안의 cascade 와 NO ACTION 검사 순서가 얽힐 수 있다) 나머지(단계·작업·체크·첨부·활동)는 DB cascade 에 맡긴다.
- **화면 데이터는 추적하지 않고 새로 읽는다**: 상세(`ViewAsync`)는 변경 응답에서도 `AsNoTracking` 으로 다시 읽어 저장된 값을 보인다. 활동은 그래프에 싣지 않고 건수·목표일 변경 횟수는 `COUNT`, 최근 활동은 필요한 열만 읽는다. Excel 은 전체 활동(`ViewAsync(id, activityLimit: null)`). 수정 화면은 기본 정보·내역만(`LoadInfoAsync`).
- **요청 안에서 기준 정보는 한 번만**: `ProjectService` 가 위치·공휴일을 요청 동안 기억한다(달력 계산과 화면의 공휴일 목록이 같은 행을 쓴다). 요청 사이에는 기억하지 않는다 — 표가 작아 얻는 것이 적고 관리 화면 변경의 무효화를 엮는 비용이 더 크다. 담당자 이름 목록은 이름 열만 읽는다.
- **보내는 양**: 응답 압축(Brotli·Gzip, `CompressionLevel.Fastest`, JSON 포함)을 정적 파일 앞에 둔다. Kestrel 단독 서비스라 앞단에서 압축해 줄 곳이 없다. 운영이 HTTP 라 `EnableForHttps` 는 기본값(꺼짐) — HTTPS 로 바꾸면 비밀 값이 든 응답의 BREACH 위험을 먼저 검토한다. JSON 인코더는 `JavaScriptEncoder.Create(UnicodeRanges.All)`(`AppJson.Encoder`, MVC 응답도 같은 것)이라 한글을 그대로 내보내면서 `<`·`>`·`&`·따옴표는 계속 이스케이프한다(페이지에 심은 JSON 이 `</script>` 로 끊기지 않는다). `UnsafeRelaxedJsonEscaping` 은 쓰지 않는다. null 필드 생략은 화면이 `=== null` 로 비교하는 곳이 있어 하지 않는다. 대시보드 간트는 쓰는 값만 담은 `TimelineView` 를 싣고(과제당 크기가 절반 이하), 간트 영역은 화면 높이 안에서 스크롤한다(`gantt-host tall`, 머리글 고정).
- **회귀 시험**: 시험 프로젝트에만 둔 `DbCommandInterceptor`(`CommandCounter`)로 상세 GET·체크 변경·대시보드의 DB 명령 수에 상한을, 대형 과제(작업 200·활동 3,000) 도우미(`BigProject`)로 상세 JSON 크기·압축률·활동 쪽 경계·변경 이력 쪽 나누기와 필터를 단언한다. 정확한 값이 아니라 상한이다(EF 버전에 따라 분할 쿼리 수가 조금 달라질 수 있다). 가짜 EF(섀도 빌드)의 `Include` 는 아무 일도 하지 않으므로 변경 경로마다 진짜 DB 로 결과를 확인하는 서비스 시험을 둔다(`DataAccessTests`).

## 8. 자동 업데이트

데스크톱 프로그램의 자기 교체 방식(매니페스트 확인 → 받기 → 검증 → 교체 → 되돌리기)을 웹 서버에 맞게 바꿨다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 누가 바뀌나 | 서버 한 곳. 브라우저는 서버가 바뀐 것을 알아채고 새로 고침만 한다 | 사용자 PC 에 깔린 것이 없다 |
| 배포 형태 | win-x64, 런타임 포함 폴더를 zip 하나로 | 서버에 .NET 을 따로 맞출 필요가 없다. 단일 exe 는 wwwroot·설정 파일과 맞지 않아 쓰지 않는다 |
| 실행 방식 | Windows 서비스(Kestrel 단독). IIS 는 대안 | 서비스는 항상 떠 있어 야간 확인·적용이 그대로 돈다(IIS 는 기본 설정에서 20분간 요청이 없으면 앱을 내린다). IIS·Hosting Bundle 을 설치하지 않아도 되고, 등록부터 업데이트 재시작까지 CI 에서 실제로 시험할 수 있다 |
| 서비스 계정 | 전용 계정 `NT SERVICE\<이름>`. 폴더 수정 권한과 자기 서비스 시작·중지 권한만 준다 | 사내망에 열린 웹 서버를 SYSTEM 으로 돌리지 않는다. 권한은 파일 교체, 교체 뒤 재시작, 시작되지 않은 새 버전을 멈추고 되돌리는 데 필요하다(예전 설치는 `install` 을 다시 실행하면 중지 권한이 더해진다. 없어도 도우미가 프로세스를 직접 끝낸다) |
| 설치 | `GanttScheduler.exe install` (`install-service.cmd`) — 실행 파일이 직접 `sc`·`icacls`·`netsh` 를 부른다 | PowerShell 스크립트는 사내 실행 정책에 막힐 수 있다 |
| 버전 확인 | `github.com/<레포>/releases/latest/download/GanttScheduler.json` → `releases/latest` 리다이렉트 → `api.github.com`(짧은 시간 제한). 앞 단계가 "없음(404)"이면 그것을 대표 원인으로 알린다 | 사내망은 api.github.com 이 막혀 있다. 막힌 주소의 시간 초과가 "응답 없음"으로 바뀌어 진짜 원인을 가리지 않게 한다. 주소·폴더로도 바꿀 수 있다(`Update:Source`) |
| 배포 위치 | 소스는 비공개 레포, 배포 파일은 공개 레포 `Gantt_Scheduler_Release` 의 릴리스 | 비공개 레포의 릴리스는 서버가 로그인 없이 읽을 수 없다. 서버에 토큰을 두지 않으려고 배포 파일만 공개한다 |
| 검증 | 매니페스트의 SHA-256 과 대조. `.partial` 로 받고 맞을 때만 풀어 둔다 | 손상·중단 파일 방지 |
| 출처 확인(서명) | 빌드에 공개키(`update-key.pub`, ECDSA P-256)가 들어 있으면 매니페스트 옆의 분리 서명(`GanttScheduler.json.sig`, SHA-256·DER)이 맞아야 받는다. 서명은 정식 배포 워크플로가 시크릿 `RELEASE_SIGNING_KEY` 로 만든다. 폴더·사내 주소 소스와 파일로 올리기도 같은 규칙(올릴 때 zip·매니페스트·서명 세 파일). 공개키가 없는 빌드는 예전처럼 SHA-256 만 보고 화면에 "서명 검증 꺼짐"을 보인다 | SHA-256 은 같은 곳에서 받은 값끼리 비교해 손상만 잡는다. 릴리스 계정·토큰이 털리면 자동 적용이 켜진 모든 서버가 남의 코드를 실행하므로, 개인키를 따로 둔 서명으로 출처를 확인한다. 공개키 파일에 키를 여러 개 둘 수 있어(하나라도 맞으면 받음) 키를 바꿀 수 있다 |
| 시작 확인 | 새 버전은 요청을 받기 시작하면(`ApplicationStarted`) `App_Data/updates/started.json` 을 남긴다. 교체 도우미는 다시 띄운 뒤 정해진 시간(기본 120초, `Update:VerifySeconds`) 안에 새 버전의 표시가 없거나 프로세스가 먼저 끝나면 실패로 본다 | 시작 명령이 받아들여진 것만으로는 새 버전이 떴는지 알 수 없다. 자동 적용은 무인 시간대에 돌아 아침까지 서버가 멈춰 있을 수 있다 |
| 시작 실패 | DB 구조가 같으면 새 버전을 내리고 이전 버전으로 되돌려 다시 띄운다. 상태 파일은 교체 전으로 돌려놓고 그 버전을 `SkipAuto`(되돌린 버전)와 새 항목 `StartFailure`(이유·시작 오류 앞부분)에 기록한다. 업데이트 화면은 이유와 "다시 시도"(받아 둔 파일로 적용 또는 다시 받기)·"안내 닫기"를 보인다. 구조가 다르면 되돌리지 않고 "백업 복원 후 이전 버전 설치"를 결과에 남긴다 | 도우미는 새 버전의 실행 파일이라 옛 서버가 띄워도 이 확인을 한다. 되돌아간 옛 버전이 이 기능을 몰라도 `SkipAuto` 는 알기 때문에 밤마다 같은 버전을 다시 적용하지 않는다. 마이그레이션이 이미 적용됐을 수 있는 경우에는 프로그램만 되돌리면 안 된다 |
| 교체 시점 | 관리자가 누를 때, 또는 설정한 시간대에 한동안 요청이 없을 때 | 서버는 "닫을 때"가 없다. 해외 법인의 근무 시간일 수 있어 시간대만으로 정하지 않는다 |
| 교체 방법 | 받아 둔 새 버전 폴더의 실행 파일을 `--apply-update` 로 따로 띄워 맡긴다 | 실행 중인 서버는 자기 파일을 바꿀 수 없다. 스크립트(PowerShell 등)는 사내 실행 정책에 막힐 수 있다 |
| 교체 범위 | 패키지 목록(`package.files`)에 있는 파일만. `App_Data`, 서버에서 고친 설정, 직접 넣은 파일은 그대로 | 데이터와 서버별 설정을 지키기 위해 |
| DB | 구조가 바뀌는 업데이트(마지막 마이그레이션이 다름)는 자동 적용하지 않고, 프로그램만 되돌리는 것도 막는다 | 마이그레이션은 시작할 때 적용되고 되돌릴 수 없다 |
| 되돌리기 | 직전 버전 한 세대 보관. 되돌린 버전은 자동으로 다시 적용하지 않는다 | 배포 사고 복구 |
| 적용 전 백업 | DB 구조가 바뀌는 업데이트는 적용을 누르면 먼저 DB 백업과 파일 묶음을 만든다(`Backup:BeforeSchemaUpdate`, 기본 켬). 백업은 요청과 떼어 돌리고(단계 `backing-up`, 화면은 상태를 다시 물어 기다린다) 끝나면 교체를 시작한다. 실패하면 적용하지 않고 이유를 보인다. 백업 이름은 교체 기록(`PendingSwap.Backup`)을 거쳐 적용 이력(`UpdateLog.Backup`)에 남고, 되돌리기가 막힌 안내에 "복원할 백업" 으로 보인다 | 구조가 바뀐 버전은 프로그램만 되돌릴 수 없어 백업이 유일한 복구 수단이다. 화면이 "백업하세요" 라고 안내만 하면 백업 여부를 확인하지 않고 적용된다 |
| 채널 | `release`(정식) · `dev`(main 시험) · `local`(로컬 빌드, 교체 안 함) | 개발 중인 폴더를 바꾸지 않도록 |

교체 순서 (`Services/UpdateApplier.cs`):

0. (DB 구조가 바뀌는 업데이트) 서버가 먼저 백업한다(`BackupService`). 실패하면 여기서 멈추고 받아 둔 업데이트는 그대로 둔다.
1. 서버가 도우미를 띄우고 1.5초 뒤 스스로 내려간다(서비스는 "중지됨" 상태가 된다).
2. 도우미가 `app_offline.htm` 을 둔다. IIS 로 운영할 때 앱을 내리고 "업데이트 중" 화면을 보여 주게 하는 파일이고, 서비스 방식에서는 쓰이지 않는다.
3. 서버 프로세스가 끝나고 실행 파일 잠금이 풀리기를 기다린다(최대 3분). 안 풀리면 아무것도 바꾸지 않는다.
4. 지금 파일을 `App_Data/updates/previous` 로 옮기고 새 파일을 복사한다. 도중에 실패하면 옮긴 파일을 되돌린다.
5. 결과를 기록하고 서버를 다시 띄운다 — 서비스는 `sc start`(실패했어도 원래 버전이 다시 떠야 하므로 항상 실행), IIS 는 다음 요청 때 스스로, 직접 실행한 서버는 같은 명령으로.
6. (적용, 서비스·직접 실행) 새 버전이 시작 표시(`started.json`)를 남길 때까지 기다린다. 시간 안에 없거나 먼저 끝나면, DB 구조가 같을 때 새 버전을 내리고(서비스 중지·남은 프로세스 종료) 보관해 둔 이전 버전으로 되돌린 뒤 다시 띄운다. 시작 오류(`App_Data/startup-error.log`)의 앞부분을 결과와 상태에 남긴다. IIS 는 도우미가 띄우지 않으므로 확인하지 않는다.
7. 다시 뜬 서버가 결과를 이력에 남기고 남은 파일을 정리한다. 성공 여부는 지금 버전이 목표 버전인지로 정한다(결과 파일은 실패 이유를 준다). 방금 적용한 받아 둔 폴더(`staged/<버전>`)는 새 버전이 요청을 받기 시작(`ApplicationStarted`)한 뒤의 정리 때 지운다 — 시작 단계를 마치고도 요청을 받기 전에 죽으면 도우미가 상태를 교체 전으로 되돌려 '다시 시도'가 그 폴더를 쓰기 때문이다(도우미 자신도 그 폴더에서 돌며 기다린다). 적용·시작 때는 받아 둔 폴더에 패키지 목록(`package.files`)의 파일이 모두 있는지 보고, 빠졌으면 버리고 다시 받게 한다.

도우미 인자는 추가만 한다. 이번에 더한 `--verify-seconds`·`--from-schema`·`--to-schema` 는 옛 도우미가 무시하고, 새 도우미는 없으면 기본값(120초, 상태 파일의 `Pending.FromSchema`, 자기 빌드의 SchemaId)을 쓴다. 서버는 시작하다 죽으면(서비스·직접 실행 모두) 원인을 `App_Data/startup-error.log` 에 남긴다.

서버가 요청을 받기 전에 하는 일(DB 마이그레이션, 직전 교체 결과 정리)은 호스트 시작 단계(`StartupWork`)에서 돌린다. Windows 서비스는 프로세스가 뜬 뒤 30초 안에 서비스 관리자에 연결해야 하는데 그 연결이 호스트 시작 때 이뤄지므로, 그 전에 DB 작업을 하면 마이그레이션이 길 때 서비스 시작이 실패한다.

### 8.1 백업 (`Services/BackupService.cs`)

| 항목 | 결정 | 이유 |
|---|---|---|
| DB | SQL Server: `BACKUP DATABASE <DB_NAME()> TO DISK=@path WITH COPY_ONLY, CHECKSUM, INIT`, 압축 없음. SQLite: `VACUUM INTO @path` | COPY_ONLY 는 DBA 의 백업 체인(차등·로그)을 깨지 않는다. Express 판은 압축을 지원하지 않는다. VACUUM INTO 는 쓰는 중에도 일관된 사본을 만든다 |
| 경로 | `Backup:Path` 는 **SQL Server 컴퓨터 기준**(절대 경로·UNC, 상대 경로는 거절). 비우면 SQL Server 의 기본 백업 폴더. 이 서버에서 그 파일을 열 수 있는 경우(SQLite, 같은 컴퓨터의 SQL Server, UNC)에만 크기 확인·정리를 한다 | BACKUP 파일은 SQL Server 서비스 계정이 그 컴퓨터에 쓴다. 원격 DB 의 `D:\Backup` 은 이 서버의 같은 이름 폴더와 다른 곳이라 건드리면 안 된다 |
| 파일 묶음 | 첨부(`Storage:Path`), 암호화 키, `appsettings.Production.json`, `backup.json`(이름·시각·버전·구조) 을 같은 이름의 zip 으로 `Backup:FilesPath`(앱 서버, 기본 `App_Data/backups`)에 | DB 만 복원하면 첨부가 404 가 된다. 짝을 맞춰 복원할 수 있게 이름(한국 시각)을 같게 한다. SQL Server 는 이름에 DB 이름을 넣는다(`gantt-<DB>-<시각>`) — 한 SQL Server 를 여러 앱이 각자 DB 로 쓰면 기본 백업 폴더가 같아 같은 초의 `INIT` 가 서로의 `.bak` 을 덮어쓴다 |
| 목록 | `Backup:FilesPath/backups.json`, 임시 파일에 쓰고 바꿔치기. 항목은 추가만 한다. 성공한 백업 `Backup:Keep`(7)개를 남기고 오래된 것은 열 수 있는 파일만 지운다. 실패 기록은 남은 가장 오래된 성공보다 새것만(최대 10) | 서버가 바뀌어도 목록을 읽고, 쓰다 끊겨도 깨지지 않게 |
| 시점 | '지금 백업'(업데이트 화면, 관리자), 구조 변경 업데이트 직전, 야간(`Backup:Nightly`, 기본 꺼짐, `Backup:NightlyAt` 한국 시간 — 하루 한 번, 실패한 회차는 다시 하지 않는다. 그 시각에 서버가 꺼져 있었으면 4시간 안에 켜졌을 때만 따라잡는다) | 사내 DB 는 DBA 가 이미 백업하는 경우가 많아 야간 백업은 기본으로 끈다 |
| 한 번에 하나 | 백업이 돌고 있으면 다른 백업 요청은 거절한다 | 같은 파일·DB 에 겹쳐 쓰지 않게 |
| 요청과 분리 | '지금 백업'은 요청 취소(탭 닫기·다른 화면으로 이동)에 묶지 않고 서버 종료에만 멈춘다. 멈춘 백업도 실패('끝나기 전에 멈췄습니다')로 목록·로그에 남는다 | 큰 DB 는 몇 분 걸린다. 백업을 누르고 다른 화면으로 가서 위험한 작업을 할 때 백업이 조용히 사라지면 안 된다 |

복원·서버 이전 절차는 [OPERATIONS.md](OPERATIONS.md).

### 8.2 운영 점검과 로그

- **점검 한 곳** (`Services/OpsChecks.cs`): 결과는 `CheckResult(이름, ok·warn·fail, 원인, 해결 방법)`. DB 왕복, DB 구조(적용된 마이그레이션 vs 이 빌드의 마이그레이션·SchemaId / SQLite 구조 표시 파일), 디스크 여유(작은 디스크는 비율, 큰 디스크는 남은 양), 폴더 쓰기 권한(App_Data·첨부·키·업데이트·로그·백업), 운영에서 SQLite 사용, PDF 글꼴(`PdfFonts` — 내보내기와 같은 탐색), 업데이트 확인 결과, 서명 검증, 첨부 대조(유실·고아·총량), 공휴일(올해, 10월부터 내년), 마지막 백업, 기준 정보. 서버 상태 화면·`/health/ready`(DB·디스크만)·관리자 칩이 같은 판정을 쓴다.
- **첨부 대조**: 과제 번호 폴더만 본다(사람이 넣은 다른 파일은 건드리지 않는다). 파일을 먼저 쓰고 DB 에 기록하는 올리기 순서 때문에 10분 안의 파일은 고아로 보지 않는다. 고아 정리는 지우기 직전에 다시 대조하고, 과제와 무관한 일이라 활동 이력 대신 로그에 누가·몇 개를 남긴다.
- **파일 로그** (`Services/FileLog.cs`, 공유 프레임워크만 써서 섀도 빌드에서도 컴파일): 한국 날짜별 `Logs:Path/yyyy-MM-dd.log`, 큐에 넣고 백그라운드에서 쓴다(요청을 늦추지 않는다). 날짜가 바뀐 뒤 처음 쓸 때 `Logs:KeepDays`(30)일이 지난 파일을 지운다. 경고 이상 최근 200건은 메모리(링 버퍼)에 둬 서버 상태 화면이 보인다. 호스팅의 요청 범위에서 요청 번호를 꺼내 줄마다 붙인다(오류 번호와 같은 값).
- **느린 요청**: `Logs:SlowRequestMs`(1000)를 넘긴 요청은 경고로 남긴다. 일부러 오래 걸리는 관리 작업(올리기·확인·백업)은 정보 수준. 성능 개선 순서를 가상 데이터가 아니라 운영 기록으로 정하기 위해서다. 모든 응답에 `Server-Timing: total;dur=<ms>`(응답을 보내기 시작할 때까지의 서버 시간)를 붙여, 사용자 PC 의 개발자 도구에서 느린 원인이 서버인지 네트워크인지 바로 가른다.
- **업데이트 진단 정보**: 업데이트 화면(관리자)에서 `apply.log` 끝 60줄, `startup-error.log`, 상태 요약(버전·단계·확인 결과·받아 둔 버전·이전 버전·진행 중 교체·시작 실패·최근 이력)과 최근 업데이트·백업 경고를 보고 텍스트 한 파일로 내려받는다. 상태 파일에 확인 성공 시각(`LastCheckOkAt`)과 실패 시작 시각(`CheckFailedSince`)을 더했다(항목 추가).

브라우저 쪽 (`wwwroot/js/app.js`):

- 모든 화면이 1분마다(보이는 탭만) `/version` 을 묻는다. 서버의 빌드가 화면을 받았을 때와 다르면 "새 버전이 적용되었습니다 · 새로 고침" 띠를 띄운다. 입력 중일 수 있어 자동으로 새로 고치지 않는다.
- 업데이트 중이라고 들은 뒤의 끊김은 안내만 하고, 예고 없는 끊김은 두 번 연속 실패했을 때 경고로 표시한다. 돌아오면 사라진다.
- 저장 요청이 업데이트 도중(503)에 걸리면 "잠시 후 다시 시도" 로 안내하고 입력 창을 닫지 않는다.
- 위조 방지 토큰의 키를 `App_Data/keys` 에 두어, 서버가 바뀐 뒤에도 열려 있던 화면에서 그대로 저장할 수 있다. Windows 서비스로 돌면 키 파일을 DPAPI(이 컴퓨터 범위)로 암호화한다. 이미 평문으로 저장된 키는 그대로 읽히고 새 키부터 암호화된다.
- 사람이 보내지 않은 요청은 "사용 중"으로 세지 않는다(자동 적용의 유휴 판단): `/version`·`/health` 와, 화면이 주기적으로 보내며 `X-Background: 1` 머리글을 붙인 요청(`App.poll` — 상세 화면의 변경 확인, 업데이트 화면의 진행 상태). 세면 상세 화면을 켜 둔 PC 하나 때문에 받아 둔 업데이트가 밤새 적용되지 않는다.

실제로 서버를 내렸다 올리는 흐름은 `tools/release/selftest.sh` 가 확인한다(확인 → 받기 → 적용 → 파일 올리기 → 되돌리기 → 시작하자마자 죽는 버전의 자동 되돌림, 데이터·설정 보존, 시험용 키로 서명 확인). Windows 서비스로 등록한 형태(운영과 같은 형태), Windows·Linux 에서 직접 실행한 형태 세 가지로 돈다.

배포 파이프라인 (`.github/workflows`):

- 정식 배포는 그 커밋의 CI(빌드·SQLite·SQL Server 테스트·화면 점검)가 성공한 경우에만 태그·릴리스를 만든다(실행 중이면 기다린다). 테스트를 다시 돌리지 않는다.
- 정식 배포와 main 의 테스트 빌드는 동시 실행 그룹이 달라, main 에 push 해도 진행 중인 정식 배포가 취소되지 않는다. 테스트 빌드(`dev`)는 CI 가 성공한 뒤에만 만든다.
- 저장소에 공개키가 있는데 서명 시크릿이 없으면 정식 배포는 태그를 만들기 전에 멈춘다. 만든 서명은 저장소의 공개키로 확인하고, 공개 레포에 올린 뒤 서버와 같은 주소로 받아 다시 확인한다.
